# 要件を先に決めて凍結する（このリポジトリ版）

⚠️ **一般的な手順は個人側の `~/.claude/skills/spec-first/SKILL.md` にある**
（同名なのでプロジェクト側のこれが優先される = **こちらが読まれる**）。
ここには**このリポジトリ固有のこと**だけを書く。重複させない。

## このリポジトリでの具体化

| 一般手順 | ここでの具体形 |
|---|---|
| 観点を分けて独立に要件を出す | **fable** で 5観点前後（作業 / セキュリティ境界 / スマホ / 依存ゼロ / 範囲）。`Workflow` で並列に |
| ドキュメントに凍結 | **`docs/<name>.md`**。実例: `docs/device-approval.md` / `docs/open-project.md` / `docs/editor-filer.md` |
| 「測ること」 | smoke（`v0/smoke.test.mjs`）/ 実ブラウザ（`*-check.mjs`）/ unit のどれで測るかまで書く |
| 「壊れ方の一覧」 | **変異の表**（名前と「何を外すか」）。`scripts/mutate.mjs` に足す |
| 実装後のレビュー | `.claude/workflows/adversarial-review.mjs`（9観点・反証つき） |
| 全部通す | `node scripts/verify.mjs`（9段） |

## このリポジトリ固有の根拠（なぜ厳しくするか）

- **凍結した回**（`device-approval` / `open-project` / `editor-filer`）は設計が実装を通して生き残った。
  実装中に崩れた前提（peer も Host も locality を証明しない）も、
  文書に「撤回した」と書き足すことで整合を保てた。
- **凍結せずに書いた回**（失効時のトークン回転）は、実装の**40分後に自分で嘘を書いた**
  （「CLI / フック … 影響なし」）。レビュー12 で**7観点が独立に同じ嘘を指摘**した。
  原因は「影響範囲を表で書いたのに、**表の各行に対応する検査が無かった**」こと。

## 変異が SURVIVED したときの見分け方（ここで何度も踏んだ）

「守りを外しても検査が落ちない」ときは、**次の2つを必ず区別する**:

1. **守りが要らなかった** → **守りごと削除する**（`defensive` で誤魔化さない）。
   実例: 配置アイコンの行指定、`shouldForgetDevice`、`openProjectWhy` の再チェック
2. **検査が弱い** → 検査を直す。よくある形:
   - **同じ結果に見える別の原因**を排除していない
     （「400 が返ったから守れている」— 実は git が失敗して 400 だった）
   - 測る対象が**そもそも存在しない**
     （textconv の検査で、対象ファイルが main では未追跡だった）
   - **字面**を assert していて、行を残して到達不能にする変更が見えない

## 忘れやすい手順

- 🚨 **写したコードには変異も写す。** 引数や門を写すと既存の変異が STALE になる。
  一意化したうえで、**写した側にも変異を足す**（足さないと新しい方は未検証）
- 🚨 **範囲を広げたら README の該当記述を同じコミットで直す**（古い記述は嘘になる）
- ⚠️ 実装後に `node scripts/mutate.mjs --dry` で**字面のずれ**を先に洗う
