# 要件を先に決めて凍結する（中くらい以上の開発）

**中くらい以上の開発は、実装の前に「要件を fable で定めて、ドキュメントに起こす」。**
書いたものを利用者が見て、そこから実装する。

## なぜ（このリポジトリで実際に起きたこと）

- **凍結した回**（`docs/device-approval.md` / `docs/open-project.md`）は、
  設計が実装を通して**ほぼそのまま生き残った**。実装中に前提が崩れた箇所も、
  文書に「撤回した」と書き足せば済んだ（peer も Host も locality を証明しない、など）。
- **凍結せずに書いた回**（失効時のトークン回転）は、実装から**40分後に自分で嘘を書いた**
  （「CLI / フック … 影響なし」）。レビュー12 で**7観点が独立に同じ嘘を指摘**した。
  影響範囲を表で書いたのに、**表の各行に対応する検査が無かった**のが原因。
- つまり凍結の効き目は「良い設計が出る」ことより、
  **主張と検査を1対1に並べさせられる**ことにある。

## いつ使うか

**中くらい以上** = 次のどれかに当たるもの:

- 🔒 **認可・capability に触る**（`--allow-*`、トークン、鍵、門の関数、判定の順序）
- 🔒 **新しい経路を足す**（HTTP のルート、子プロセス、リポジトリ外の読み書き）
- 変更が**複数ファイルに跨る**、または **UI とサーバの両方**に及ぶ
- 「**やり方が2通り以上あって、どちらも一理ある**」と感じた
- 見積もりが**コミット2本以上**になりそう

使わなくてよいもの: 誤字、1関数の中で閉じる修正、既存の検査に1件足すだけ、
すでに凍結済みの設計に沿った実装の続き。

⚠️ **迷ったら使う。** 凍結の費用は文書1枚だが、凍結しなかったときの費用は
「レビューで7観点に同じ嘘を指摘される」だった。

## 手順

### 1. fable で要件を定める（制限下では Opus でよい）

観点を分けて **fable の独立したエージェント**に出させる。1エージェント1観点にして、
互いの結果を見せない（共有すると全員が同じ穴を見つけて他が抜ける）。

⚠️ **fable が利用制限下のときは Opus で設計してよい**（利用者の許可。2026-08-18）。
**凍結しないより凍結する方が価値が大きい**ので、モデルが理由で止まらない。

🚨 ただし **fable を使う目的は「独立性」**だったので、Opus で書いたときは
それが1つ落ちていることを自覚して補う:

| | fable | Opus（制限下の代替） |
|---|---|---|
| 独立性 | 実装者と別のモデル | **実装者と同じモデル = 自分の盲点は見えない** |
| 補い方 | そのまま | ①観点ごとに**別のサブエージェント**にして互いの結果を見せない ②文書に**「要件は Opus で起こした」と明記** ③実装後の**敵対的レビューを省略しない**（元々必須だが、ここでは特に） |

⚠️ **「fable が制限だったから」を、検査を省く理由にしない。**
このセッションの嘘（「CLI / フック … 影響なし」）は**モデルの問題ではなく、
表の行に対応する検査を書かなかった**ことが原因だった。

出させるもの:

- **利用者が本当に困っていること**（言われた解決策ではなく、その手前）
- **不変条件**（これを壊すなら設計をやり直す、という線）
- **やらないこと**（範囲を切る。ここを書かないと実装中に膨らむ）
- **代替案と、それを採らない理由**
- 🔒 認可に触るなら **門の順序**（何を先に判定するか）と**その理由**

⚠️ **fable の出力をそのまま貼らない。** 矛盾と過大主張を自分で潰してから書く
（エージェントは「もっともらしい設計」を出すが、このリポジトリの過去の事故を知らない）。

### 2. `docs/<name>.md` に起こす

**必ず入れる節**（`docs/device-approval.md` と `docs/open-project.md` が実例）:

| 節 | 中身 |
|---|---|
| 何が問題か | 利用者の言葉を引く。日付を入れる |
| なぜこの形か | **採らなかった案とその理由**（後から「なぜこうした」を再現できるように） |
| 不変条件 | 🔒 で始める。壊すなら設計をやり直す線 |
| 門の順序 | 表にする。**各段が「なぜその位置か」**を書く |
| 置き場所と記録 | ファイル・権限・監査に何を残すか |
| **測ること** | 箇条書き。**実装と同じコミットで**入れる |
| **変異** | 名前と「何を外すか」の表 |
| やらないこと | 範囲の外側を明示する |

🚨 **「測ること」と「変異」を書かずに凍結しない。** ここが空の文書は、
主張だけがあって検査が無い状態を**そのまま実装に持ち込む**。

🚨 **影響範囲を表で書いたら、表の各行に対応する検査があるかを確認する。**
レビュー12 の嘘（「フックは影響なし」）は、**その行にだけ検査が無かった**。

### 3. 利用者に見せて確定させる

トレードオフが残っているなら**選択肢と推奨**を出して聞く。
⚠️ 「どちらも一理ある」を黙って自分で決めない。ただし
**利用者が「判断できない」と言ったら、こちらで決めて理由を書く**（丸投げしない）。

### 4. 実装する

凍結した文書のとおりに作る。**実装中に前提が崩れたら、コードではなく文書を先に直す**。

- 前提を撤回したら、文書に**撤回したと明記して理由を残す**（消さない）
- 設計と違う形にしたなら、**なぜ変えたか**を文書に追記してから実装を続ける
- 変異が SURVIVED したら、**守りが要らなかったのか / 検査が弱いのか**を見分けて、
  前者なら**守りごと削除**する（`defensive` で誤魔化さない）

### 5. 実装が終わったら

`node scripts/verify.mjs` が全段緑 → 変異が KILLED → **敵対的レビュー**
（`.claude/workflows/adversarial-review.mjs`）。
認可・capability に触ったなら、レビューは**必須**。

## やってはいけないこと

- ❌ **文書を実装の後に書く**（後追いの文書は実装の言い訳になる。嘘に気付けない）
- ❌ **「測ること」を空にして凍結する**
- ❌ **fable の出力をそのまま docs にコピーする**
- ❌ 凍結した文書と違う実装をして、文書を放置する（**どちらかが必ず嘘になる**）
