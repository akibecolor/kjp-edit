## BLOCKING

### A1 🛑 スパイク手順書に書いた対処が、公開済み CVSS 8.8 の RCE を設定で再現する

spikes.md S2 Step 7 の FAIL 1 対処として
「`ElectronSecurityToken` を**未設定にする**」「`THEIA_ELECTRON_VERSION` を設定して
デーモンに自分を Electron だと思わせる」と書いていた。レビュー側が Theia `master` の
3ファイルを実際に読んで指摘:

- `browser-connection-token.ts` — `allowWsUpgrade()` は `if (environment.electron.is()) { return true; }` で始まる
- `electron-token-validator.ts` — `if (!this.electronSecurityToken) { return true; }`
- `ws-request-validators.ts` — 集約は **fail-open**（どれかが明示的に `false` を返さない限り `true`）

**この2つを組み合わせるとクッキーゲート回避 → トークン検査回避 → 誰も異議を唱えない fail-open 許可。
`/services/shell-terminal` を含む全 RPC が任意オリジンに開放される。**

これは **GHSA-78g8-vm3p-97c6**「Cross-Origin WebSocket Access To Shell-Terminal
Enables Command Execution And Output Exfiltration」CVSS **8.8**、1.73.0 で修正済みを、
設定で再現する行為。しかも `THEIA_ELECTRON_VERSION` 偽装は
**そのデーモンに繋ぐ*すべての*ブラウザフロントエンド（`/` と `/m` の両方）に対して
same-origin 検証を破壊する**ことに、元の記述は一切触れていなかった。

**修正済み**（spikes.md に🛑ブロックを追加、正しい対処は「デーモン側がトークンを生成して
Electron main に渡す」+ `THEIA_HOSTS` 明示 + 起動時アサーション）。

### A2 🛑 `persist:preview` の緩和策は D6 が選んだ描画経路に実装できない

viewer.md は「iframe の唯一の弱点は `session.fromPartition('persist:preview')` で消せる。
**ただしアプリ全体では絶対にやらない**」と書き、同じ文書の v1 推奨は
「通常の Theia `ReactWidget` 内の **`<iframe>`**」。

`partition` は webContents のプロパティで、**素の `<iframe>` は親 webContents 内のフレーム。
iframe 単位のパーティションは存在しない。** よってヘッダ除去はウィンドウのセッションに
登録するしかなく、それは自分が太字で禁止した「アプリ全体でのクリックジャッキング防御除去」。
副作用でプレビューが IDE のクッキージャーとストレージを共有する。

**修正済み。デーモン側リバースプロキシでヘッダ書き換えする案に変更**
（A8 でどうせプロキシが必要なので追加コストが小さく、Electron のセッションを改変せず、
**ブラウザプライマリとセカンダリでも同じ挙動になる**）。

### A3 🛑 制御プレーンに認証が無く、Theia が過去に出した CVE と同形

`/api/v0/stat`（任意パスの stat）と `/api/v0/terminals`（シェル生成、`{} as any` で
オプション検証なし）に**認証も `Origin` チェックも `Host` チェックも無い。**
これは **CVE-2019-17636**（`@theia/mini-browser` 8.1 HIGH、HTTP エンドポイントによる
無制限のファイルシステムアクセス、DNS rebinding や drive-by で悪用可能）と同じ形。
そして PR #17701 は「ターミナル生成オプションを検証・サニタイズする」ことも追加しているのに、
`{} as any` はそれを捨てている。

さらにサブドメイン分離では `theia-connection-token`（`sameSite: 'strict', path: '/'`）を
守れない（SameSite は登録可能ドメイン単位）。

**必要な対処:** プレビュー分離は**別サイト**（異なる登録可能ドメイン）であること。
制御プレーンは**非アンビエントな資格情報**（`Authorization` ヘッダか
`Sec-WebSocket-Protocol` トークン）を使うこと。
**全 `/api/v0/*` と upgrade ハンドラに fail-closed な `Host` + `Origin` allowlist を、
最初のスパイクコミットで入れること。**

コンポーネントに直結すると書き直しになる**。`DiagramRenderer` インタフェース経由にせよ」と書き、
同時に「Streamdown を採用」と書いていた。

**`streamdown@2.5.0` の実 dependencies に `mermaid ^11.12.2` がある。
Streamdown を採用することがまさにその直結。** 最大リスクの緩和策が、
レンダラを選んだ瞬間に無効化される。加えて KaTeX が存在せず、Shiki は devDep のみ、
`marked ^17` が dependency（remark/rehype 前提の比較表と違う）、`rehype-raw` で生HTML有効。

### #2 🛑 D1 は記述通りには成立していない

D1 は「クライアント↔コアのプロトコルを自前で定義し、ローカルUIとリモートPWAは*同一の*
プロトコルを話す。**リモートモードを作らない — ローカルUIをクライアント#1にする**」と書いている。

だがプライマリは Theia フロントエンドで、**Theia の socket.io/Inversify RPC を話す** —
同じ文書が「手書きクライアントから使ってはいけない」と書いたプロトコル。
**つまりプロトコルは2つあり、ローカルUIは特権経路。** kjp-core の機能はすべて二重に公開が必要。

加えて「**ドキュメントモデル（開いているバッファ、dirty状態）← 権威**」も成立しない。
`FileService` はフロントエンド専用で、dirty 状態は Theia の `saveableService`/Monaco
モデル（フロントエンド）に住んでいる。

**修正案:** D1 を正直に「**クライアント2種・トランスポート2種・権威1つ**」と書き直す。
そして権威の範囲を「ファイルシステム + レジストリ、ドキュメントモデルはフロントエンド毎」に
縮めるか、Theia の saveable/editor スタックを rebind する工数を計上する。

### #3 🛑 ズーム機構の評価が誤りで、Phase 2 の受入テストは「ゲート2つ」では通らない

上記「既に修正した事実誤認 3」の通り。**修正済み**だが、
**Phase 2 の受入テストは「Zed の issue リストに相当する状況を手で再現してどれも起こらないこと」**
だったので、**Phase 2 の実現性が未確定に戻った。**
S1 に「ファイルツリーを見えたまま単一エディタタブをズームする」（#32715 / #27237 相当）を
追加する必要がある。

### #4 🛑 Phase 1 の完了条件が Phase 5 のインフラを要求し、127.0.0.1 のみの規則に違反する

Phase 1 の完了条件は「別端末のブラウザから同じバックエンドに繋がる」。
だが `127.0.0.1` のみのバインド、TLS、OIDC、ケイパビリティ分離は**すべて Phase 5**。
つまり **セキュリティモデルが1つも存在しない段階で、リモート端末にフル機能の
Theia ワークベンチ（無制限のシェルとFS）を渡す。**
Phase 5 の完了条件「ターミナル権限は明示的に付与しない限り無い」と正面衝突する。

**修正案:** Phase 1 の完了条件を「手で張った SSH/tailscale トンネル経由で
2つ目のブラウザが繋がる（閲覧経路のみ）」に変え、**loopback 限定バインドを Phase 1 に移す。**

### #5 🛑 「エージェントを tmux セッション内で走らせる」は「ACP stdio サブプロセス」と両立しない

D1 は「デーモン再起動を越えた生存は tmux か abduco でバックする。
**エージェントをその永続セッションの中で走らせれば**長時間実行が生き残る」と書き、
D4 は「ACP (stdio JSON-RPC) : kjp-core ⟷ エージェントサブプロセス」と書いている。

**tmux 内の PTY は端末ストリームであって構造化パイプではない。**
再アタッチして JSON-RPC を拾うのは、D4 が禁じた「TUI のスクレイプ」そのもの。
そして依存しようとしている `session/resume` with replay は **ACP v2 の機能**で、
自分で「v1 をターゲットし v2 は機能フラグの背後に置く」と決めている。

さらに research.md 自身が「**tmux/zellij を埋め込むのは避ける** —
キーバインド名前空間とレンダリングを継承して自前のタイリング層と喧嘩する」と書き、
dtach/abduco を正しいプリミティブとして挙げているのに、D1 と技術スタック表は
「tmux か abduco」を対等に並べている。

**修正案:** tmux/abduco は**ユーザのターミナルのみ**をバックする。
エージェントのデーモン再起動越えの生存は (a) ACP v2 の `session/resume`（v1 には無いと明記）か
(b) デーモンがトランスクリプトを永続化して新しいエージェントプロセスに再プロンプトする、
のどちらか。**「エージェントを永続セッション内で走らせる」を削除し、tmux を落として abduco/dtach にする。**

## SERIOUS（抜粋、severity 順）

### A4 ケイパビリティ分離は装飾的 — 3つの迂回路があり、うち1つは意図的に作っている

「リモートクライアントは承認はできるが任意シェル起動は withhold できる」という主張に対して:

1. **承認＝実行。** 承認されたのはツールコール。**どのパスへの書き込みを許すかを何も制約していない。**
   `.git/hooks/post-commit`、`package.json` の `postinstall`、`.claude/settings.json`、
   `.vscode/tasks.json`、devcontainer ファイルへの承認済み書き込み1回で、
   次の通常操作で任意シェルになる。リモートクライアントはターミナルを要求すらしない
2. **`/acp` がターミナルAPIそのもので、意図的に公開している。**
   ACP **v1 にはクライアント側 `terminal/create` と `fs/write_text_file` がある**
   （v2 で削除されたと自分で書いている）。**v1 の `/acp` をモバイルに公開することは、
   Phase 5 の完了条件が「無い」と言っている capability を、
   認証モデルを規定していない2つ目の制御プレーンで配ること**
3. **`attach(id)` が無防備**（下記 A5）

**修正案:** 境界をエンドポイントではなく**効果**で定義する。
リモート capability セッションは構造的に (i) 実行トリガとなるパスクラスへの書き込み、
(ii) `/acp` への到達、(iii) 自分が作っていないターミナルへの `attach` ができないこと。

### A5 `attach(id)` の「機能でもある」という整理は、インターネット到達可能なクライアントには通らない

1. **IDは列挙可能。** 整数ID空間が1つなので `for id in 1..N`
2. **attach は遡及的な窃取。** 1MB の `MultiRingBuffer` がリプレイされるので、
   **一度も触っていないターミナルの `env` 出力・`gh auth token`・kubeconfig・
   `aws sts` レスポンスが読める**
3. `DispatchingBaseTerminalClient` が exit/error を全クライアントにファンアウト = liveness oracle

そして D2 の「入力は排他、明示的 takeover」は**クライアント側の約束**を、
「所有権チェックを一切しない」サーバ呼び出しの上に重ねているだけ。

**修正案:** デーモンが terminal→session の ACL を持つ。
**`ProcessManager` の整数IDをワイヤプロトコルに絶対出さない**（推測不能なハンドルにする）。
スクロールバックのリプレイをライブ attach とは別にゲートする。

### A6 localhost プレビュープロキシの露出列挙が、価値の高い3経路を落としている

- **(a) プロキシは構成上 SSRF プリミティブ。Theia は既にこのCVEを出している** —
  **GHSA-2m57-xxmh-v696**（CVSS 8.5、`BackendRequestFacade`、1.73.0 修正、
  「宛先URLが検証もallowlistもされていない典型的なSSRF」）。**どこにも引用が無かった。**
  ポート単位オプトインではリダイレクト追跡・チェックと接続の間の DNS rebinding・
  `[::1]`/`0.0.0.0`/`169.254.169.254` の正規化をカバーしない
- **(b) 入れ子 HMR `Upgrade` はコードプッシュチャネル。** HMR ソケットは
  `update`/`full-reload` を配り、クライアントはそれをサーバ供給モジュールURLの `import()` に変える。
  **トンネルされた HMR ソケットを話せる者はプレビューオリジンでコードを実行できる。**
  元の記述は「工数リスク」としてしか扱っていなかった
- **(c) Eruda + 要素ピッカーは意図的なスクリプト注入で、戻りチャネルが未規定。**
  Theia には **CVE-2021-41038「Webview contents can be hijacked via postMessage()」**がある。
  `event.origin` チェックもセッション毎 nonce もメッセージスキーマも、どの文書にも無い
- **(d) ピッカーのペイロードがエージェントの文脈に入る = 二次注入。**
  共有クッキージャー（v3・オプトイン）は正しく識別しているが、**こちらは v1 で無ゲートで出荷される**

**そして事実誤認1つ:** 「Vite の `/@fs` 任意ファイル読み取り」は既定を誇張している。
`server.fs.strict` は Vite 2.7 以降既定 true で `/@fs` はワークスペースルート内に閉じている。
実際の露出は2025年のバイパスCVE群。緩和策は正しいが根拠が正しくない。

### A8 「`127.0.0.1` のみ ⇒ 構造的に不可能」は誤りで、既定が無認証デーモン

loopback バインドは1つの誤設定に対する緩和であって構造的性質ではない。
トンネル終端自体が loopback クライアントなので、**ホスト上に既にいるもの
（他のローカルユーザ、ホストネットワークのコンテナ、そして
`Host` チェックが無いので DNS rebinding 経由の任意のWebページ）には何の境界にもならない。**
そして D7 が「アカウントなしで完全に動く」を保証している = **大半のユーザにとって
トンネル前の状態が既定かつ恒久的な状態**であり、そこに「自前WSは認証が無い」が重なる。

**修正案:** **loopback を含めて無条件に資格情報を要求する。**
Electron は 0600 のトークンファイルから読む（`~/.claude/ide/<port>.lock` パターンを
自分で記述している）。`Host` allowlist を追加。「構造的に不可能」を実際に防げるものに書き換える。

### B2 「ACPモバイルクライアント4つがタダで手に入る」は自分の表と矛盾している

research.md 自身が「**トランスポート: stdio 上の JSON-RPC** が SHOULD ベースライン…
**Streamable HTTP はドラフト。WebSocket 無し**」と書いている（レビュー側が
`agentclientprotocol.com/protocol/v1/transports.md` で再確認）。
そして secondary-client.md の表では4クライアントが**トランスポートも認証方式も共有していない**
（直接 wss+bearer / ローカルゲートウェイ / TweetNaCl リレー / 暗号化リレー）。

**`/acp` over WS は非標準トランスポートで、せいぜい1つが到達可能、

### #6 D2 のリースとケイパビリティ分離はターミナルに対して強制不能

プライマリは Theia 自身の RPC でターミナルに到達し、`attach()` に所有権チェックが無い。
**kjp-core はその経路上に居ないので何も強制できない。**
「意図的に決めること」と2箇所に書いてあるが**決めていないし、どのフェーズも
「`IShellTerminalServer` を rebind してリースを強制する」を持っていない。**

**修正案:** Phase 3 に項目追加 — `IShellTerminalServer`/`ITerminalServer` を
kjp-core のガード背後に rebind し、ID レジストリ・所有権・リース・
リモートのシェル起動 capability を kjp-core が持つ。

### #7 D7「サインアップ不要」はローカル限定のプライマリにしか成立せず、QRペアリングは自分の禁止事項と衝突

D7 は「ホスト型リレーを必須にしない、`tailscale serve` 経路を対等に並置する」と書くが、
**Tailscale はクローズドなコントロールプレーンのアカウントが必要**、OIDC は IdP アカウント、
ホスト型リレーは SaaS、自己ホストの逃げ道（Headscale/frp/VPS）も別のアカウントが必要。

そして **D7 の「QRに鍵材を載せたペアリング」は、同じ文書のセキュリティ表の
「静的ベアラトークンは使わない — シェル履歴・**QRコード**・スクリーンショットに漏れる」と衝突。**

**修正案:** D7 を「**機能ごとに誰のアカウントが必要か**」の表に書き直す
（プライマリ=なし / tailscale経由=Tailscale ID / リレー経由=リレー運営者 or 自己ホスト+VPS /
自前リバースプロキシ=ドメイン+ACME+IdP）。QRペアリングは
「短命・デバイス束縛・1回限り・失効可能」（同じ表が v0 トークンに要求している条件）に揃えるか、どちらかを落とす。

### #8 「プレビューは別オリジンから配信、交渉不可」が推奨リモート経路と両立しない

`tailscale serve` は**ホスト名が1つ**で、MagicDNS 名の下の per-uuid サブドメインには
証明書経路が無い。しかも「HTTPS は交渉不可」。
そして **theia#16275（browser ターゲットでは webview がサンドボックス組み合わせでブロックされる）**を
自分で「早めに確認する」と書いたのに、**Phase 0 にスパイクが無い。**

**修正案:** theia#16275 のスパイクを Phase 0 に追加。リモート経路のオリジン戦略を決める
（おそらくデーモン側プロキシが**別パス**でプレビューを配信 + 厳格CSP + `Origin` チェック、
かつワイルドカードサブドメイン分離は Electron/ローカル限定と明記）。
「別オリジン、交渉不可」を「得られる場所では別オリジン、それ以外はサンドボックス+CSP+資格情報なし」に格下げ。

### #9 D6 の決め手「iframe なら同一コンポーネントがセカンダリでも動く」は D5 により偽

D5 はセカンダリを Theia 無しの別実装にし、D7 制約4 は
「セカンダリ用のコード・依存はプライマリのバンドルに入れない」と書き、
viewer.md の v1 は iframe を **Theia `ReactWidget` 内**に置き（セカンダリは
インスタンス化できない）、secondary-client.md のパネル一覧は3つでブラウザパネルが無く、
ヘッダ除去は Electron 限定。

**D6 の判断自体は D3 クリッピングの論拠だけで生き残るが、対称性の主張は生き残らない。**
（ただし A2 の修正でヘッダ書き換えをデーモン側プロキシに移すと、
**対称性の主張は部分的に本当になる** — 共有されるのは framework 非依存の
`<iframe>` ラッパと Markdown レンダラであって `ReactWidget` ではない、と明記すれば。）

### #10 git エンジンが2つ、SCM UI が2つ共存し、共存判断が永久に先送りされている

「gitの変更操作は例外なく worktree の排他ロックを取る」と書きながら、
`vscode.git` 駆動の SCM ビューとコミットDAGを、デーモンが見えも制御もできない
接続毎プラグインホスト内に残す。**要件は「1つのアプリ」なのに、
git エンジン2つと履歴UI2つを出荷する。** しかもタブが2つなら `vscode.git` のコピーも2つ =

「最初に決める」と書いてあるが**どのフェーズも所有していない。**

**修正案:** Phase 0/1 で決めて書く。他と整合する安い答え —
製品ビルドで `@theia/scm` のビューと `vscode.git` の履歴グラフを無効化/非表示にし、

か出荷拡張セットから除外する。

### #11 research.md は要件5（多数の並列パネル）に CM6 が正しいと結論しているが、architecture.md は Monaco を選んでモバイル論点にしか答えていない
