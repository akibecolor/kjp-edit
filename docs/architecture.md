# アーキテクチャ設計

前提となる調査結果は [research.md](research.md)。ここでは設計判断とその理由だけを書く。

## 設計の核となる5つの判断

| # | 判断 | 一行の理由 |
|---|---|---|
| **D1** | コアは**ヘッドレスデーモン**。ローカルUIもリモートUIも同じプロトコルを話す対等なクライアント | 「リモートモード」を作らない。クライアントは1種類だけ作り、ローカルUIをクライアント#1にする |
| **D2** | 状態は**サーバ権威**。CRDTは使わない | ファイルシステムは物理的に1つしかない。調停するものが無い |
| **D3** | レイアウトは**単一のコンテナツリー**。dock/pane の区別を作らない | Zed の分かりづらさの根本原因がこの非対称性 |
| **D4** | エージェントは **ACP** 経由。デーモンがACPクライアントかつファンアウト点 | 35エージェントが既にネイティブ対応。CLIラッパ8個を書かない |
| **D5** | セカンダリ（モバイル）は**ワークベンチを載せず別実装の軽量クライアント**にする | 縦積み折りたたみは Theia の設定では得られない。Jupyter が同じ道を試して撤回済み。Monaco のモバイル問題もこれで消える |
| **D6** | ビューア（ブラウザ/Markdown）は **iframe 既定**。`WebContentsView` はタイル単位のオプトイン | ネイティブオーバーレイは D3 の単一ツリーと根本的に衝突する。iframe なら同一コンポーネントがセカンダリでも動く |

## D1: プロセス構成

```
                     プライマリ機（すべてを所有）
  ┌───────────────────────────────────────────────────────────┐
  │  kjp-core デーモン（長寿命・すべてのUIより長く生きる）        │
  │   ・ワークスペース/worktree レジストリ + git エンジン        │
  │   ・ドキュメントモデル（開いているバッファ、dirty状態）← 権威 │
  │   ・イベントバス → N購読者へファンアウト                    │
  │   ・エージェントスーパバイザ（ACPクライアント、worktree毎）  │
  │   ・LSP スーパバイザ                                       │
  │   ・HTTP + WebSocket、127.0.0.1 のみ にバインド             │
  └──┬──────────────┬───────────────┬──────────────┬─────────┘
     │ 子プロセス     │ 子プロセス      │ 子プロセス     │ loopback WS
  ┌──▼──────┐ ┌─────▼──────┐ ┌──────▼─────┐ ┌────▼──────────┐
  │ pty host│ │file watcher│ │ LSP procs  │ │ トンネル終端    │
  │(全PTY)  │ │(@parcel)   │ │            │ │ tailscale serve│
  └─────────┘ └────────────┘ └────────────┘ │ / Caddy+oauth2 │
                                             └────┬──────────┘
     ┌────────────────┐                           │ TLS + OIDC + ACL
     │ PRIMARY UI     │──── loopback WS/IPC       │
     │ Electron       │                    ┌──────▼─────────┐
     │ ネイティブ性能  │                    │ SECONDARY: PWA │
     └────────────────┘                    │ 別PC/タブレット │
                                            └────────────────┘
```

### 具体的な決定事項

**1. 1プロトコル・2トランスポート。**
クライアント↔コアのプロトコルを自前で定義する（WebSocket上のJSON-RPC + イベントストリーム）。
opencode がやっているように OpenAPI/スキーマを公開する。
ローカルUIとリモートPWAは*同一の*プロトコルを話す。
**「リモートモード」を作らない — クライアントモードだけを作り、ローカルUIをクライアント#1にする。**
これは Theia の洞察であり、Theia が単一コードベースから browser と Electron を
ターゲットできる理由でもある。

**2. pty は専用の pty-host サブプロセスがコアの下で所有する**（VS Code の形）。
pty のクラッシュがコアを殺さないため。
**デーモン再起動を越えた生存とOS レベルの堅牢性は、セッション復活を自作せず
tmux か abduco/dtach でバックする。** エージェントをその永続セッションの中で走らせれば、
長時間のエージェント実行がすべてを生き残る。
VS Code はこれをやらず「プロセス永続性が必要なら tmux か screen を使え」と
ドキュメントに書いており、その結果「VS Code のターミナルを tmux で包む」ブログ記事が
一大産業になっている。同じ穴を掘らない。

**3. ファイル監視は専用ユーティリティプロセス**で @parcel/watcher。
VS Code の重複排除・除外・サスペンド/ポーリング設計をそのまま踏襲する（research.md 参照）。
イベントは**ツリーのパッチ**に合体させ、全体リフレッシュを絶対に起こさない。

**4. 再接続はエラー経路ではなく第一級の状態機械。**
クライアントは最後に見たイベントシーケンス番号を保持し、コアはセッション毎に
有界のリプレイバッファを持つ。再接続時にクライアントは自分のカーソルからリプレイする。
これは ACP v2 の `session/resume` with replay と全く同じパターンで、正しい設計。

## D2: マルチクライアントの意味論

ここが素朴な設計が壊れる場所。**明示的に決めておく必要がある。**

| | 決定 |
|---|---|
| **プレゼンス** | 全クライアントが「他にどのクライアントが繋がっているか」を見られる |
| **レイアウトは共有しない** | セカンダリにプライマリのタブ構成をミラーさせない。**「同じ環境」とは「同じ共有ワークスペース状態 + クライアント毎のアクティブビュー」**を意味する。さもないとスマホを使うとデスクトップが勝手に動く。そもそも3画面デスクトップとタブレットは違うレイアウトが欲しい |
| **共有される状態** | ファイルシステム、git状態、worktree、開いているバッファの内容とdirty状態、ターミナルセッション、エージェントセッションとその出力 |
| **書き込みリース** | バッファ毎にソフトリース、worktree毎にハードリース。**gitの変更操作（rebase / merge / branch操作）は例外なく worktree の排他ロックを取る** |
| **ターミナルのアタッチ** | 閲覧者はN人可。ただし**入力は排他とし、明示的な takeover が必要**（tmux の非共有モードと同じ）。さもないとキーストロークが交互に混ざる |
| **インテントは冪等かつバージョン付き** | 再接続してリプレイしたときにコミットやマージが二重適用されないように |

**なぜCRDTを使わないのか。**
権威的サーバが1つあるときCRDTが買うのは3つだけで、そのうち我々に関係するのは
「高RTTリンクでのローカルエコー」だけ。それは**クライアント側予測 + サーバ調停**
（バージョン付き編集、却下されたらrebase）で解ける。ゲームが昔からやっていること。
CRDTを基盤にすると、git・ターミナル・エージェントプロセスのどれにも合わないデータモデルを
全サブシステムに強制することになる。Zed がCRDTをリモート開発に使っているのは、
`Buffer` 型が既にコラボ用のCRDTだったからという無料の再利用に過ぎない。

真のマルチユーザコラボを後で追加したくなったときに Yjs を足す。それまでは足さない。

## D3: レイアウト — 単一コンテナツリー

**これが差別化の核であり、Zed への直接の回答。**

### モデル

i3/sway と同じ。すべてがコンテナ。コンテナは1つのコンテンツか子コンテナ群を保持する。

```
Node =
  | { kind: 'split', orientation: 'h' | 'v', children: Node[], sizes: number[] }
  | { kind: 'tabs',  children: Node[], activeIndex: number }
  | { kind: 'leaf',  panelId: string, panelType: string }

Layout = {
  root: Node,
  focusedNodeId: NodeId,
  zoomedNodeId: NodeId | null,   // ← ツリーの外ではなくルートに1つ
}
```

**leaf のコンテンツ型に階層を作らない。** エディタ・ターミナル・ファイルツリー・
コミットグラフ・エージェントセッション・差分ビュー・出力パネル — すべてが同格の `panelType`。
**「サイドバーに置けるもの」と「エディタエリアに置けるもの」の区別を作らない。**
これが Zed（および VS Code）の非対称性の除去。

### 5つの設計ルール

Zed の失敗を機構レベルで回避するために、以下を守る。根拠は research.md の
「Zed のレイアウトが分かりづらい理由」節。

1. **ズームは1ノードに対するビュー変換であり、兄弟の状態変更ではない。**
   ルートの `zoomedNodeId` を見て、そのサブツリーのみを100%で描画する。
   **どこのサイズにも触らない。** ズーム解除は無変更のツリーを再描画するだけ。
   → Zed のバグ #21776（分割でズーム状態が失われ発振する）と
   #47207（余白が増え背後の要素が見える）が構造的に起こり得なくなる

2. **ズーム中の構造変更は、サブツリー内で作用するか暗黙にズーム解除する。両方はしない。**

3. **すべてのパネルが同一ツリーに入る。** ズームが「dockを丸ごと隠す」しかない状況を作らない。
   → #32715（ファイルツリーを残したままエディタをズームできない）が起こらない

4. **サイズは比率ではなく、そのsplitノード内での明示的な配分として保持し、
   構造変更で再正規化しない。** tmux のズーム意味論に倣い、直前のジオメトリを厳密に記憶して
   バイト単位で復元する。リフローも比例圧縮もしない。
   → #52584（パネルが変に細くなる）が起こらない

5. **`focus parent` を実装する。** i3 の `$mod+a` 相当。ツリーを1階層上がり、
   次の分割/移動/クローズが葉ではなく*サブツリー*に作用する。
   **これが無いと「任意にネスト可能」はキーボードから使い物にならない。**
   多くのWebレイアウトライブラリに欠けている概念で、ここが実装の要。

### キーボードコマンド（i3/tmux 由来）

`split-h` / `split-v` / `focus-{left,right,up,down}` / `focus-parent` / `focus-child` /
`move-{left,right,up,down}` / `zoom-toggle` / `resize-{grow,shrink}` /
`layout-{splith,splitv,tabbed}` / `swap` / `close` / `popout`

Zellij に倣い**常時表示のキーバインドバー**を置く。
キーボード駆動タイリングUIにおいて最も安価で効果の高いUX改善。

### レイアウト状態の永続化

Obsidian の `workspace.json` と同じ。**レイアウトは継続的に永続化される単なるJSONツリー**として扱い、
変更ごとに書き直す。**クライアント（デバイス）毎に別のレイアウトを保存する** — D2の通り、
レイアウトは共有しない。

### 実装ライブラリ

Theia ベースなら **Lumino DockPanel** が既にこのモデルの大部分を提供する。
ただし `ApplicationShell` の left/right サイドパネルは `'single-document'` モードで分割不可なので、
**ルール3（すべて同一ツリー）を満たすには `ApplicationShell` をサブクラス化して
左右エリアも `TheiaDockPanel` の `'multiple-document'` にする必要がある。**
これは Theia の DI で公式にサポートされた拡張点（コアサービスの rebind とシェルのサブクラス化）だが、
**どれだけの改変で済むかは Phase 0 のスパイクで測る。**

Theia を採らない場合は **dockview 7.x**（MIT、ネスト+タイル内タブ+ポップアウト+
真の maximize API を全部持つ唯一のライブラリ）の上に自前のコマンド層を載せる。
あるいはコンテナツリーを完全に自作して **allotment**（VS Code の splitview/sash 由来なので
リサイズ挙動が正しい）でサッシュだけ描く — ツリーモデル自体は400〜600行程度で、
i3の意味論を「近似」ではなく「厳密に」得られ、直列化も自分のものになる。
捨てるのは dockview のドラッグ&ドロップオーバーレイとポップアウト配線で、これが高価な20%。

## D4: エージェント統合

### 層構造

```
ACP (stdio JSON-RPC) :  kjp-core ⟷ エージェントサブプロセス   ← worktree毎、1:1
自前プロトコル (WS)   :  kjp-core ⟷ N クライアント            ← マルチクライアント
```

**デーモンが ACP クライアントであり、ファンアウト点。**
ACP自体をマルチクライアントトランスポートにしようとしない — stdioサブプロセス志向で
マルチクライアント/リモート/再接続の意味論を持たず、仕様と喧嘩する。
ただし ACP v2 の `session/resume`-with-replay と `state_update` モデルは
*我々自身の*プロトコルの再接続意味論の良いテンプレート。**設計を盗み、プロトコルを引き伸ばさない。**

**ACP v1 をターゲットし、v2 は明示的なバージョンネゴシエーションと機能フラグの背後に置く**
（ACP移行文書がそう助言している）。v2 がクライアント側 fs/terminal を削除して
エージェント所有ターミナルにしたのは所有権の大きな再構成だが、
**偶然にも我々のサーバ権威デーモンとよく整合する。**

### 隔離モデル

**worktree/エージェント**を既定にする（先行事例の事実上の標準）。
コンテナ隔離（Sculptor / container-use 方式）は後から足せるオプションにする。
worktree レジストリはデーモンが所有し、git変更操作は worktree の排他ロックを取る（D2）。

### エージェント認証の製品判断

**Claude Agent SDK を埋め込むと API キー前提になる。**
Anthropic のポリシー: 「事前承認がない限り、サードパーティ開発者が自社製品に
claude.ai ログインやレートリミットを提供することは許可されない。Claude Agent SDK 上に
構築されたエージェントを含む。API キー認証を使用せよ。」

Conductor / Crystal / Sculptor が「自分のサブスクを持ち込め」を売りにできているのは、
**SDKを埋め込まずユーザ自身の `claude` CLI をシェルアウトしているから。**

→ **ACP 経由でユーザのローカルCLIバイナリをサブプロセスとして起動する方式を採る。**
これは (a) 認証がユーザの手元に留まり、(b) ACPのトランスポートモデルと一致し、
(c) 特定ベンダに縛られない、の三重の利点がある。SDK直接埋め込みは選ばない。

ブランディング: 「Claude Code」「Claude Code Agent」は製品名に使えない。
「Powered by Claude」形式は可。

### やってはいけないこと

**CLI の TUI をスクレイプしない。** research.md の淘汰データがこれを裏付けている —
Omnara は CLIラッパ方式を「保守が不可能になった」として放棄し Agent SDK に書き直した。
ccmanager はエージェント毎に8種類の状態検出戦略を抱えている。
ACP がまさにこの作業を殺すために存在する。

## コミットグラフと履歴編集 — 最大の差別化要素

research.md の G1: **コミットグラフ中心の履歴操作UIを持つツールが1つも無い。**
エージェントは大量に形の悪い履歴を生むので、ここが日常の急所。

### 実装方針

**バックエンド:** `git` をシェルアウトする。
`git log --topo-order --all -z --pretty=format:%H%x00%P%x00%an%x00%at%x00%s` を
ストリームして逐次パース。`core.commitGraph` を有効化し `git commit-graph write` を打つ
（10万コミット超の走査に対する単独最大の効果）。
走査完了を待たず最初の画面を描く。nodegit と isomorphic-git は却下（理由は research.md）。

**レーン割当:** v1 は **VS Code の `scmHistory.ts` (MIT) の swimlane パスを移植**する。
小さく、許諾的で、実戦検証済み。曲がりが気になってきたら
pvigier の **straight-branches**（`J_i(c)` リスト最適化版、実測274ms）に差し替える。

**順序付け:** git の `--topo-order` に任せる。自前で順序を付ける必要が出たら
pvigier の **temporal topological sort**（committer date の新しい順に訪れるトポロジカルソート。
妥当・決定的・タイムスタンプが正常なら日付順を保持・O(n log n + m)）を実装する。
素のトポロジカルソートは非決定的でグラフが目に見えて並び替わるので使わない。

**描画:** 行を仮想化し、可視ビューポートのみ描く。可視エッジはインターバルツリーで区間重複クエリ。
pvigier の実測で全描画106ms → 可視ノードのみ26.8ms → 可視ノード+エッジ0.580ms の**180倍**。
10万コミットの成否はここで決まる。
v1 は VS Code 式（行毎に小さなSVG）、レーン数が増えたりタブレットで慣性スクロールが欲しくなったら
**ハイブリッドcanvas**（グラフ列だけcanvasレイヤ、テキスト列は仮想化DOMをスクロール同期）に移行する。
**大きなSVGを1つ作ることは絶対にしない。**

**⚠️ `mhutchie/vscode-git-graph` のコードには一切触れない。**
LICENSE 実文が「derivative works を publish, distribute, sublicense, sell する許可は与えない」と
明記している。MITと書いている三次情報は間違い。fork (hansu/) も同じ制限を継承する。

### 履歴編集UI（ここが空白）

グラフを起点に:
interactive rebase / コミットの並べ替え / squash / **コミットの分割** /
**過去のコミットへの fixup** / worktree 間の cherry-pick / **reflog 救出**。

「40個の『fix tests』コミットを3つのレビュー可能なコミットに整形する」を
グラフ上の直接操作でできるようにするのが目標。

### クロスエージェントレビュー（G4）

5エージェントがそれぞれブランチを出したときの比較的な問い —
どの2つが同じファイルを触ったか / マージでどれが衝突するか / マージ順序はどうすべきか。
コミットグラフは既に全ブランチを1枚に描いているので、**この情報の自然な表示面**になる。
これがグラフ中心設計の副産物としての利点。

## リモートアクセス

### 露出の設計

1. **デーモンは `127.0.0.1` のみにバインドする。** `0.0.0.0` にしない。
   リモート到達はすべてループバックで終端するトンネル/オーバーレイ経由。
   これで「うっかりLANやインターネットに出ていた」が構造的に不可能になる
2. **既定の推奨は Tailscale `tailscale serve`** — NAT越え、WireGuard級のピアID、
   安定ホスト名、自動HTTPS を一手で得られ、開放ポートはゼロ。
   `tailscale funnel` は**使わない**（公開してしまう）
3. **代替経路をドキュメント化する**: Cloudflare Tunnel + Access（難点: ソースコードと
   ターミナルのトラフィックがCFのTLS終端エッジを通る）、SaaS拒否派には
   Headscale / zrok / frp / rathole
4. **自前のリレーは作らない。** MicrosoftのDev Tunnelsリレーも
   VS Code Serverバイナリもライセンス上使えない（research.md）
5. **セカンダリはインストール可能な PWA として出荷する。**
   これがブラウザのキーバインド衝突に対する単独で最も効果の高い対策
   （code-server FAQ が明示している）。加えて
   「エージェントが承認を待っている」のpush通知が使える
6. **HTTPS は交渉不可。** webview的なサンドボックスiframeを使うなら
   service worker が secure context を要求する。`tailscale serve` か Caddy で自動化

### セキュリティ — 前提の認識

**我々が公開しようとしているのは、SSH鍵・クラウド認証情報・ソースコードを持つマシン上の、
無制限のシェルとファイルシステムアクセスを持つエージェント + ターミナルである。**
これは設計上リモートコード実行エンドポイントであり、認証バイパス1つで開発者マシンの完全な侵害。

| | |
|---|---|
| **ネットワーク層の認可を第一線に** | Tailscale ACL / WireGuard ピアIDなら未認証パケットは届かない。アプリ認証は多層防御であって唯一の線ではない |
| **アプリ認証は OIDC** | forward-authプロキシ（`oauth2-proxy`）か Cloudflare Access 経由。**静的ベアラトークンは使わない** — シェル履歴・QRコード・スクリーンショット・ブラウザ履歴に漏れ、期限が来ない。v0でトークンを出すなら短命・デバイス束縛・失効可能・1回だけ表示。IdPで2FA必須 |
| **ケイパビリティ分離** | ターミナルとエージェント承認の面を**別々にゲートする**。リモートクライアントはエージェント出力を*見る*ことと*承認/拒否*はできるが、「任意シェルを起動」は**リモートセッションからwithholdできる別の権限**にする。Anthropic が Claude Code Remote Control で選んだパターンがこれ |
| **レート制限とロックアウト** | code-server の 2/分・12/時 は*床*であって模範ではない |
| **監査ログ** | リモート起因のコマンドを全て記録 |

## D5: セカンダリはワークベンチを載せず、別クライアントにする

**決着済み。** 詳細と根拠は [secondary-client.md](secondary-client.md)。要点だけ:

**モバイルには Theia のワークベンチを載せない。同一バックエンドに対する別実装の軽量クライアントを立てる。**

これは D1（1プロトコル・クライアントは1種類）が既に想定していた形であり、
**Monaco のモバイル問題はセカンダリが Monaco を使わないことで消滅する。**

判断の根拠:

1. **縦積み折りたたみリストは Theia の設定では得られない。** シェルは `DockPanel` +
   `SidePanelHandler` + `BoxLayout` でスタック/アコーディオンモードを持たない。
   カスタム `ApplicationShell` を書くことになり、その時点で新フロントエンドを書いたのと同じだが、
   Theia の内部と 1.27 型の破壊的変更に結合してしまう
2. **Jupyter が同じ道を試して撤回している。** JupyterLab は Lumino シェルをレスポンシブ化して
   出荷し（PR #8456, 2020-05）、8ヶ月後に撤回した（PR #9831, 2021-02）— 理由は
   「レスポンシブレイアウト・モバイルプラットフォーム・シンプルインタフェースという
   別々の問題を混同していた」。代わりに **Notebook 7** を出し、そのシェルは
   **`DockPanel` を使わず** `BoxLayout` + `SplitPanel` の手書き簡易シェルになっている。
   同じ Lumino、同じサーバ、同じプラグイン、違うシェル
3. **Theia / Microsoft / Coder の3者がこの要望を5〜7年抱えて誰も出荷していない。**
   レスポンシブなワークベンチは見落としている小さな作業量ではない
4. Monaco と xterm.js のモバイル問題を完全に回避できる。差分はHTML、エージェント出力はDOM、
   ターミナルログは `<pre>`、指示入力は `<textarea>`

デプロイは Jupyter のパス別マルチフロントエンド（`/lab`, `/tree`, `/nbclassic` が1サーバから）を踏襲:

```
kjp-core デーモン
  ├── /     → プライマリ: Theia ワークベンチ (Electron / デスクトップブラウザ)
  ├── /m    → セカンダリ: 軽量モバイルクライアント（別実装）
  └── /acp  → ACP over WebSocket
```

**`/acp` を公開する理由:** ACP モバイルクライアントが既に4つOSSで存在する
（Agmente/iOS/MIT, Ferngeist/Android/MIT, Happy/全プラットフォーム/MIT, Mobvibe/Apache-2.0）。
そして Ferngeist のドキュメントが ACP エコシステム最大の実務上の制約を突いている —
**「ほとんどの ACP エージェントは stdio しかサポートしていない。まず WebSocket ブリッジでラップせよ」。**
kjp-core がネイティブにそのブリッジになれば、書かなくて済むモバイルクライアントが4つ手に入る。

## ⚠️ D1 の訂正: Theia のバックエンドプロトコルは手書きクライアントから使えない

**Theia のフロントエンド↔バックエンドプロトコルは内部実装詳細。**
ドキュメントのページ名は「JSON-RPC」だが、#10514 (2021-12) で transport が socket.io に移行し、
その上に Theia 独自の多重化チャネルフレーミングが乗っている。
**RPC層は Theia 1.27 で書き直され、それ以前の方式を使う全拡張が壊れた。**
外部消費者向けのバージョニングも互換性の保証も存在せず、両端で Inversify を前提にしている。

Theia 自身のドキュメントが正解を示している —
「フロントエンドとバックエンドの通信にはどのプロトコルも使える。
バックエンドは自分のエンドポイントを登録・公開できる」。

→ **kjp-core は「自前のバージョン付き WS/HTTP エンドポイントを公開する Theia backend 拡張」として実装し、
その内部で Theia の注入済みサービス（`FileService`、terminal、SCM、task、LSPプロキシ）を
通常の Inversify DI で消費する。** Theia のサービス実装は使うが、そのワイヤフォーマットには依存しない。

足場として **`@theia/plugin-ext-headless`** がある。ここのプラグインは、フロントエンド接続毎に
ホストを起こす `@theia/plugin-ext` と違って**全フロントエンドで共有される1つの
バックエンドホストプロセスに住む** — まさに必要なスコープで、公式の意図もそう書かれている。

（`@theia/collaboration` / Eclipse Open Collaboration Tools は**これではない。**
Live Share 型の P2P ライブ*共有*プロトコルで、マルチクライアント対単一バックエンドではない。beta 警告付き。）

## D6: ビューアパネル

設計と根拠は [viewer.md](viewer.md)。要点だけ:

**埋め込みブラウザは `<iframe>` を既定の描画経路にする。`WebContentsView` は
タイル単位のオプトインな能力アップグレードにとどめる。**

**なぜ D3 と衝突するのか:** `WebContentsView`（および deprecated な `BrowserView`）は
**DOM に存在せず、常に最前面で、コンテナにクリップされない。**
Electron でフルのブラウザを作ったチームは、この結果として
**ドロップダウン・モーダル・ツールチップごとに別のビューを作り、
main プロセスに Facebook Yoga でレイアウトエンジンを再実装した。**
ドラッグ分割・タブ並べ替え・コマンドパレット・コンテキストメニューを持つ
再帰的タイリングツリーは、この方式にとって最悪のケース。
**任意のスクロール祖先にクリップするAPIは存在しない — 直せるバグではない。**

iframe の唯一の弱点（X-Frame-Options / CSP `frame-ancestors` でブロックされる）は
Electron 側で消せる — 専用の `persist:preview` パーティションで `onHeadersReceived` により
該当ヘッダを除去する（**アプリ全体では絶対にやらない**。クリックジャッキング防御の無効化なので）。

そして決定的な利点として、**iframe なら同一コンポーネントがセカンダリ（モバイル）でも動く。**
この対称性は `WebContentsView` の単一機能より価値が高い。

`WebContentsView` に昇格する価値があるのは、本物の `enableDeviceEmulation`、
`setDevToolsWebContents` による本物の Chrome DevTools タイル、クロスオリジンの `capturePage`、
エージェント用CDPが必要になったときだけ。その場合は
**スプリッタドラッグ中・タブドラッグ中・オーバーレイが開いている間は `setVisible(false)`** を
ハードルールにする。

**Theia の既存資産と注意点:**
- `@theia/mini-browser` は本物の Lumino ウィジェットで iframe ベース。オーバーレイ問題ゼロで正しくタイルされる。
  **ただし公開されたRCEアドバイザリがあり、`{{uuid}}.mini-browser.{{hostname}}` による
  オリジン分離は任意ではなく必須**
- `@theia/preview` は **deprecated かつ npm 未公開**。Theia の markdown preview では Mermaid が描画されない
- **theia#16275: `allow-same-origin` + `allow-scripts` の組み合わせにより
  *browser* アプリでは webview がブロックされる（Electron では起きない）。
  この非対称性は2クライアント設計を刺すので早めに確認する**

**Markdown レンダラは自作する（Theia/VS Code のものを使わない）。**
両方とも*ファイル指向*でストリーミングの概念を持たないが、
**我々の主要ユースケースはまさにそれ — エージェントは設計文書やレポートをストリームする。**
実装は **Streamdown (Apache-2.0)** に乗る（remark/rehype + GFM + 未完成markdown処理 +
`rehype-harden` + KaTeX + Shiki + Mermaid の配線が1依存で入る）。

⚠️ **エージェントの出力は半信頼。** プロンプトインジェクションでエージェントが
`<img onerror=…>` を書き、それを我々が描画しうる。サニタイズし、
**プレビューはサンドボックス化された別オリジンのフレームで描画する。**

⚠️ **Mermaid の描画場所は Markdown パネルを書く前に決める。**
~1.5〜2.7MB で DOM を要求し、動的ESMインポートが Electron のパッケージングと喧嘩し、
**軽量なはずのセカンダリを軽量でなくする張本人。**
プラガブルな `DiagramRenderer` インタフェース（クライアント側 mermaid / デーモン側 Kroki）を
最初から設計し、両方が同じコンテンツハッシュSVGキャッシュに供給する形にしておく。

## Monaco のタッチ非対応の実レベル（プライマリには影響しない）

セカンダリが Monaco を使わないので設計上の争点ではなくなったが、
デスクトップブラウザ経由でタブレットから触る可能性があるので実レベルを記録しておく。
全文は [secondary-client.md](secondary-client.md)。

| 操作 | 判定 |
|---|---|
| 描画・タッチドラッグスクロール（慣性含む） | **問題なし**（実装されている） |
| タップでカーソル配置 | **問題なし** |
| **テキスト選択** | **構造的に破綻。** 選択が偽のdivでフォーカスが画面外textareaなのでネイティブハンドルを付ける対象が無く、かつ1本指ドラッグはスクロールに使い切られている。設定では直らない |
| 入力 | Android は「不器用だが使える」（EditContext 既定化で改善しているはず）。**iOS Safari は EditContext 非対応で旧来の問題を保持** |
| ページのスクロール継続 | 破綻（エディタが末端でもスクロールを消費する）。固定高ペインに独自スクロール領域を与えれば回避 |

**読み取り専用なら実用になる:** `{ readOnly: true, domReadOnly: true }` で
ソフトキーボードが一切開かなくなり、iOS の ShowKeyboardWidget も抑止される。

**実機評価: iPad+キーボード ≒ 不器用だが使える（コピペが頻繁に壊れる） / スマホ ≒ 閲覧専用。**
GitLab は Monaco製 Web IDE で壁に当たり、モバイル用に Ace ベースの単一ファイルエディタを残した。
