# 端末を承認して登録する（実行の鍵を毎回貼らないために）

**利用者の要件（2026-08-09）:** 「鍵を毎回入れるのが面倒。Google 認証を使えないか」
→ 検討の結果、**Google 認証は使わない**。理由は下の「なぜ OAuth ではないのか」。
採る形は利用者自身の言葉どおり「**サーバー側で許可動作を行ったもののみ**」＝
**母艦で承認した端末にだけ、その端末専用の鍵を発行する**。

⚠️ この文書は**実装より先に順序を決める**ためのもの。
認可は順序そのものが守りで、この repo は**順序で2回事故**を起こしている
（`--allow-exec` の門が自動生成より後ろにあった / 検査用経路が Host 検証より前にあった）。

---

## 1. 何が面倒なのか（正確に）

| | 今の保存先 | 寿命 | 面倒か |
|---|---|---|---|
| 読み取りの鍵（派生秘密） | Cookie | 1年 | **一度だけ**。面倒ではない |
| 実行の鍵（生トークン） | `sessionStorage` | **タブを閉じるまで** | **毎回貼る** ← これ |

`sessionStorage` にしているのは意図的で、根拠は
「**Cookie はポートで分離されない**（RFC 6265）ので、`http://127.0.0.1:3000` の
任意のローカルページが Cookie を焼ける／読める経路に乗る。渡っても読み取りまでに留める」。
つまり**面倒さは守りの代償**であって、単に寿命を伸ばすと守りが消える。

## 2. なぜ OAuth（Google）ではないのか

1. **tailnet のログインが既に Google アカウント。** スマホが届いている時点で
   「Google で認証された端末」であることは確定していて、もう一度聞いても**情報が増えない**
2. 🚨 **identity ヘッダを信用できない。** `tailscale serve` は**ループバックに繋ぎ直す**ので、
   サーバから見た相手は `127.0.0.1`。同じマシンの別プロセスが
   `Tailscale-User-Login` と `Host:` を付けて叩けば**区別できない**。
   ヘッダを信じた瞬間に、読み取りも実行も丸ごと取られる
   （今 Host 検証で防いでいる DNS rebinding と同じ構図）
3. OAuth を自前で実装すると、クライアントシークレット・リダイレクト URI・JWKS の検証が
   **ローカルデーモンの攻撃面**として増える。依存パッケージゼロの制約とも相性が悪い

**結論: 認証の相手は「人」ではなく「端末」。承認は母艦でしか押せない。**

## 3. 不変条件（これを壊すなら設計をやり直す）

1. 🔒 **端末の鍵を Cookie に入れない。** `localStorage`（**ポートを含むオリジン単位**）に置く。
   Cookie に入れた瞬間、他ポートのローカルページに渡る
2. 🔒 **承認はループバックからしか押せない。** トンネル越しの要求で承認が完了してはいけない
   （でないと「届いた相手が自分を承認する」になる）
3. 🔒 **承認は capability を増やさない。** `--allow-exec` が無ければ、承認済みの端末でも実行は 403。
   承認が意味を持つのは「**この端末に、既に有効な capability を使わせてよいか**」だけ
4. 🔒 **鍵の照合は必ず `tokenWall()` を通す**（混雑の門 → 比較 → 外したら記録して遅延）。
   新しい照合経路を門の外に作らない（#63 で踏んだ形）
5. 🔒 **長寿命にするなら失効が要る。** 一覧・失効・最終使用時刻を**同じコミットで**作る
   （「緩めた守りの代わりを同じコミットで置く」）
6. ⚠️ **承認していない端末は今までどおり**（読み取りは Cookie、実行は鍵を貼る）。
   既存の経路を壊さない

## 4. 流れと門の順序

```
[スマホ]                         [デーモン]                    [母艦の画面]
  登録したい ──POST /pair/request──▶ 読み取り認証を通す
                                    要求を1件だけ保持（TTL 5分）
                                    合言葉（6桁）を返す ──────▶ 同じ合言葉を出す
  合言葉を表示                                                   「承認 / 拒否」
                                 ◀──POST /pair/approve──────── ループバック＋実行の鍵
  ポーリング ──GET /pair/status──▶ 承認済みなら端末鍵を1回だけ返す
  localStorage に保存
  以後 x-kjp-token で提示 ──────▶ tokenWall → 実行が通る
```

**順序の理由:**

| 段 | 何を要求するか | なぜその位置か |
|---|---|---|
| 1. `/pair/request` | 読み取りの認証（既存の入口） | 誰でも要求を積めると、母艦の画面が承認待ちで埋まる（DoS） |
| 2. 合言葉の一致 | 母艦と端末に**同じ6桁**を出す | 同時に2件来たとき、**どれを承認したか**を人が確かめられる |
| 3. `/pair/approve` | **ループバック** かつ **生の実行トークン** | トンネル越しに承認させない（不変条件2）。実行の鍵を要求するのは、承認が実行を配る操作だから |
| 4. `/pair/status` | 要求時に配った一時 id | 承認結果を**要求した端末だけ**が取れる |
| 5. 端末鍵の提示 | `tokenWall()` | 総当たりに記録と遅延を付ける（#63） |
| 6. `/pair/list` `/pair/revoke` | 生の実行トークン | 失効は実行と同じ重さの操作 |

⚠️ **1件だけ保持する。** 承認待ちを積み上げない（積むと「どれを承認したか」が曖昧になる）。
新しい要求は古い要求を**上書きし、上書きしたことを画面に出す**。

## 5. 置き場所と記録

- `~/.kjp-edit/devices.json`（0600）。`{ id, label, secretHash, createdAt, lastUsedAt, revokedAt }`
  - 🔒 **平文の鍵を保存しない**（`sha256` を保存し、提示された値を照合する）
- 監査（`exec-audit.jsonl`）に `pair-request` / `pair-approve` / `pair-reject` /
  `pair-revoke` / `pair-first-use` を残す。**鍵そのものは書かない**
- `label` は端末が名乗る自由文なので**長さと文字種を縛る**（記録に自由文を入れない原則）

## 6. 測ること（実装と同じコミットで）

- 承認前は端末鍵が**無い**ので実行は 403 のまま
- 承認後は**貼らずに**実行できる（再読込しても続く）
- 🔒 **トンネル越し（`Host:` が許可ホスト名）からは `/pair/approve` が拒否される**
- 🔒 **読み取りの鍵だけでは `/pair/approve` も `/pair/list` も通らない**
- 失効したら**その端末だけ**が通らなくなる（他の端末は生きる）
- 端末鍵が **`Set-Cookie` に出てこない**（不変条件1を字面でなく応答で測る）
- 合言葉が母艦と端末で一致する／5分で期限切れになる
- 総当たりに記録と遅延が付く（`tokenWall` を通っている）

変異（守りを外すと落ちること）:
`pair-approve-from-tunnel`（ループバック判定を外す）/
`pair-approve-read-key`（実行の鍵の要求を外す）/
`pair-secret-in-cookie`（Cookie に入れる）/
`pair-no-revoke`（失効を無視する）/
`pair-wall-bypass`（`tokenWall` を通さない）

## 7. これができると「プロジェクトを開く」が同じ土台に乗る

利用者の要件③（ローカルのプロジェクトを開く）は、今は**意図的に禁じている**
（「UI から任意のパスを開く経路は作らない」）。承認の仕組みができれば
「**開く = 承認つきでリポジトリを登録一覧に足す**」として同じ門に乗せられる。
先に承認を作るのはそのため。

## 8. やらないこと

- 複数ユーザ・権限分離（個人用ツール。`docs/scope.md`）
- 端末鍵の自動失効（期限）— **最終使用時刻は持つが、切るのは人の判断**。
  黙って切れると「動いていたものが動かない」になり、原因が分からない
