# 端末を承認して登録する（実行の鍵を毎回貼らないために）

**利用者の要件（2026-08-09）:** 「鍵を毎回入れるのが面倒。Google 認証を使えないか」
→ 検討の結果、**Google 認証は使わない**。理由は下の「なぜ OAuth ではないのか」。
採る形は利用者自身の言葉どおり「**サーバー側で許可動作を行ったもののみ**」＝
**母艦で承認した端末にだけ、その端末専用の鍵を発行する**。

⚠️ この文書は**実装より先に順序を決める**ためのもの。
認可は順序そのものが守りで、この repo は**順序で2回事故**を起こしている
（`--allow-exec` の門が自動生成より後ろにあった / 検査用経路が Host 検証より前にあった）。

---

## 1. 何が面倒なのか（正確に）

| | 今の保存先 | 寿命 | 面倒か |
|---|---|---|---|
| 読み取りの鍵（派生秘密） | Cookie | 1年 | **一度だけ**。面倒ではない |
| 実行の鍵（生トークン） | `sessionStorage` | **タブを閉じるまで** | **毎回貼る** ← これ |

`sessionStorage` にしているのは意図的で、根拠は
「**Cookie はポートで分離されない**（RFC 6265）ので、`http://127.0.0.1:3000` の
任意のローカルページが Cookie を焼ける／読める経路に乗る。渡っても読み取りまでに留める」。
つまり**面倒さは守りの代償**であって、単に寿命を伸ばすと守りが消える。

## 2. なぜ OAuth（Google）ではないのか

1. **tailnet のログインが既に Google アカウント。** スマホが届いている時点で
   「Google で認証された端末」であることは確定していて、もう一度聞いても**情報が増えない**
2. 🚨 **identity ヘッダを信用できない。** `tailscale serve` は**ループバックに繋ぎ直す**ので、
   サーバから見た相手は `127.0.0.1`。同じマシンの別プロセスが
   `Tailscale-User-Login` と `Host:` を付けて叩けば**区別できない**。
   ヘッダを信じた瞬間に、読み取りも実行も丸ごと取られる
   （今 Host 検証で防いでいる DNS rebinding と同じ構図）
3. OAuth を自前で実装すると、クライアントシークレット・リダイレクト URI・JWKS の検証が
   **ローカルデーモンの攻撃面**として増える。依存パッケージゼロの制約とも相性が悪い

**結論: 認証の相手は「人」ではなく「端末」。承認の根拠は「母艦でしか読めない合言葉」。**

## 3. 不変条件（これを壊すなら設計をやり直す）

1. 🔒 **端末の鍵を Cookie に入れない。** `localStorage`（**ポートを含むオリジン単位**）に置く。
   Cookie に入れた瞬間、他ポートのローカルページに渡る
2. 🔒 **承認の根拠は「母艦でしか読めないものを読めたこと」。**
   ⚠️ **当初ここには「承認はループバックからしか押せない」と書いていたが、これは実装できない**
   （2026-08-09 に実測して撤回した）。`tailscale serve` はループバックに繋ぎ直すので、
   トンネル越しの要求も `req.socket.remoteAddress === '127.0.0.1'` になり、
   `Host` は要求側が自由に決められる:

   | 送り方 | peer | Host |
   |---|---|---|
   | ローカルの素 | `127.0.0.1` | `127.0.0.1:58889` |
   | Host を偽装 | `127.0.0.1` | `fractal2.tail73c198.ts.net` |
   | 逆に偽装 | `127.0.0.1` | `127.0.0.1:9999` |

   **peer も Host も「母艦にいること」を証明しない** — identity ヘッダを退けたのと同じ理由。
   なので承認の根拠を**合言葉の出口**に置く: デーモンは合言葉を
   **自分の stdout と `~/.kjp-edit/pair-code`（0600）にだけ**書き、
   **要求した端末には返さない**。合言葉を知れる = 母艦のコンソールか
   ホームディレクトリを読めた、なのでネットワークの偽装では越えられない
3. 🔒 **承認は capability を増やさない。** `--allow-exec` が無ければ、承認済みの端末でも実行は 403。
   承認が意味を持つのは「**この端末に、既に有効な capability を使わせてよいか**」だけ
4. 🔒 **鍵の照合は必ず `tokenWall()` を通す**（混雑の門 → 比較 → 外したら記録して遅延）。
   新しい照合経路を門の外に作らない（#63 で踏んだ形）
5. 🔒 **長寿命にするなら失効が要る。** 一覧・失効・最終使用時刻を**同じコミットで**作る
   （「緩めた守りの代わりを同じコミットで置く」）
6. ⚠️ **承認していない端末は今までどおり**（読み取りは Cookie、実行は鍵を貼る）。
   既存の経路を壊さない

## 4. 流れと門の順序

```
[端末]                          [デーモン]                     [母艦の人]
  登録したい ──POST /pair/request──▶ 読み取り認証を通す
                                    要求を1件だけ保持（TTL 5分）
                                    合言葉を **stdout と 0600 のファイル**へ ──▶ 読む
                                    （応答には**合言葉を載せない**）        （serve.mjs --pair）
  合言葉を入力 ──POST /pair/claim──▶ id と合言葉を照合（tokenWall + 試行5回）
                                    一致 → 端末の鍵を**1回だけ**返す
  localStorage に保存
  以後 x-kjp-token で提示 ──────────▶ tokenWall → 実行が通る
```

**順序の理由:**

| 段 | 何を要求するか | なぜその位置か |
|---|---|---|
| 1. `/pair/request` | 読み取りの認証（既存の入口） | 誰でも要求を積めると、母艦の合言葉が上書きされ続ける（DoS） |
| 2. 合言葉の出口 | **stdout と 0600 のファイルだけ** | ここが「母艦にいること」の証明。応答に載せた瞬間に設計が崩れる |
| 3. `/pair/claim` | id + 合言葉 / **`tokenWall()`** / **試行5回** | 6桁は 100 万通りなので、記録・遅延・上限の3つで守る。上限を超えたら**要求そのものを無効**にする |
| 4. 鍵の受け取り | **1回だけ** | 再送で漏れる面を作らない（渡したら要求を閉じる） |
| 5. 端末鍵の提示 | `tokenWall()` | 総当たりに記録と遅延を付ける（#63） |
| 6. `/pair/list` `/pair/revoke` | **生の実行トークン**（端末の鍵では通さない） | 承認された端末が**他の端末を消せる／一覧できる**状態にしない |

🚨 **端末の鍵は「実行を通す」が「生トークンの払い出しは通さない」。**
`/api/v0/session` が返す生トークンは `tokenMatches()`（生の値）だけに出す。
ここを混ぜると、承認した端末が生トークンを回収して**別の端末を承認できる**。

⚠️ **1件だけ保持する。** 承認待ちを積み上げない（積むと「どれを承認したか」が曖昧になる）。
新しい要求は古い要求を**上書きし、上書きしたことを画面に出す**。

## 5. 置き場所と記録

- `~/.kjp-edit/devices.json`（0600）。`{ id, label, secretHash, createdAt, lastUsedAt, revokedAt }`
  - 🔒 **平文の鍵を保存しない**（`sha256` を保存し、提示された値を照合する）
- 監査（`exec-audit.jsonl`）に `pair-request` / `pair-claimed` / `pair-bad-code` /
  `pair-too-many` / `pair-revoke` / `pair-first-use` を残す。**合言葉も鍵も書かない**
- `label` は端末が名乗る自由文なので**長さと文字種を縛る**（記録に自由文を入れない原則）

## 6. 測ること（実装と同じコミットで）

- 承認前は端末の鍵が存在しないので実行は 403 のまま
- 承認後は**貼らずに**実行できる（再読込しても続く）
- 🔒 **応答に合言葉が載らない**（`/pair/request` の本文と `/pair/status` の両方）
- 🔒 **合言葉を外し続けると要求が無効になる**（5回）。無効化後は正しい合言葉でも通らない
- 🔒 **他人の id では受け取れない**（相乗りできない）
- 🔒 **読み取りの鍵だけでは `/pair/list` も `/pair/revoke` も通らない**
- 🔒 **端末の鍵では `/api/v0/session` の生トークンを取れない**（承認の連鎖を作らない）
- 失効したら**その端末だけ**が通らなくなる（他の端末は生きる）
- 端末の鍵が **`Set-Cookie` に出てこない**（字面ではなく応答で測る）
- 合言葉の照合が `tokenWall()` を通っている（記録と遅延が付く）

変異（守りを外すと落ちること）:

| 名前 | 何を外すか |
|---|---|
| `pair-code-in-response` | 応答に合言葉を載せる |
| `pair-no-try-limit` | 試行の上限（5回）を外す |
| `pair-id-not-checked` | id の照合を外す（相乗りできる） |
| `pair-list-accepts-device` | 端末の鍵で一覧・失効を通す |
| `pair-session-token-to-device` | 端末の鍵に生トークンを渡す（承認の連鎖） |
| `pair-secret-in-cookie` | 端末の鍵を Cookie に入れる |
| `pair-wall-bypass` | `tokenWall()` を通さない |

## 7. これができると「プロジェクトを開く」が同じ土台に乗る

利用者の要件③（ローカルのプロジェクトを開く）は、今は**意図的に禁じている**
（「UI から任意のパスを開く経路は作らない」）。承認の仕組みができれば
「**開く = 承認つきでリポジトリを登録一覧に足す**」として同じ門に乗せられる。
先に承認を作るのはそのため。

## 8. やらないこと

- 複数ユーザ・権限分離（個人用ツール。`docs/scope.md`）
- 端末鍵の自動失効（期限）— **最終使用時刻は持つが、切るのは人の判断**。
  黙って切れると「動いていたものが動かない」になり、原因が分からない
