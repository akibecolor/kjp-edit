# 端末を承認して登録する（実行の鍵を毎回貼らないために）

**利用者の要件（2026-08-09）:** 「鍵を毎回入れるのが面倒。Google 認証を使えないか」
→ 検討の結果、**Google 認証は使わない**。理由は下の「なぜ OAuth ではないのか」。
採る形は利用者自身の言葉どおり「**サーバー側で許可動作を行ったもののみ**」＝
**母艦で承認した端末にだけ、その端末専用の鍵を発行する**。

⚠️ この文書は**実装より先に順序を決める**ためのもの。
認可は順序そのものが守りで、この repo は**順序で2回事故**を起こしている
（`--allow-exec` の門が自動生成より後ろにあった / 検査用経路が Host 検証より前にあった）。

---

## 1. 何が面倒なのか（正確に）

| | 今の保存先 | 寿命 | 面倒か |
|---|---|---|---|
| 読み取りの鍵（派生秘密） | Cookie | 1年 | **一度だけ**。面倒ではない |
| 実行の鍵（生トークン） | `sessionStorage` | **タブを閉じるまで** | **毎回貼る** ← これ |

`sessionStorage` にしているのは意図的で、根拠は
「**Cookie はポートで分離されない**（RFC 6265）ので、`http://127.0.0.1:3000` の
任意のローカルページが Cookie を焼ける／読める経路に乗る。渡っても読み取りまでに留める」。
つまり**面倒さは守りの代償**であって、単に寿命を伸ばすと守りが消える。

## 2. なぜ OAuth（Google）ではないのか

1. **tailnet のログインが既に Google アカウント。** スマホが届いている時点で
   「Google で認証された端末」であることは確定していて、もう一度聞いても**情報が増えない**
2. 🚨 **identity ヘッダを信用できない。** `tailscale serve` は**ループバックに繋ぎ直す**ので、
   サーバから見た相手は `127.0.0.1`。同じマシンの別プロセスが
   `Tailscale-User-Login` と `Host:` を付けて叩けば**区別できない**。
   ヘッダを信じた瞬間に、読み取りも実行も丸ごと取られる
   （今 Host 検証で防いでいる DNS rebinding と同じ構図）
3. OAuth を自前で実装すると、クライアントシークレット・リダイレクト URI・JWKS の検証が
   **ローカルデーモンの攻撃面**として増える。依存パッケージゼロの制約とも相性が悪い

**結論: 認証の相手は「人」ではなく「端末」。承認の根拠は「母艦でしか読めない合言葉」。**

## 3. 不変条件（これを壊すなら設計をやり直す）

1. 🔒 **端末の鍵を Cookie に入れない。** `localStorage`（**ポートを含むオリジン単位**）に置く。
   Cookie に入れた瞬間、他ポートのローカルページに渡る
2. 🔒 **承認の根拠は「母艦でしか読めないものを読めたこと」。**
   ⚠️ **当初ここには「承認はループバックからしか押せない」と書いていたが、これは実装できない**
   （2026-08-09 に実測して撤回した）。`tailscale serve` はループバックに繋ぎ直すので、
   トンネル越しの要求も `req.socket.remoteAddress === '127.0.0.1'` になり、
   `Host` は要求側が自由に決められる:

   | 送り方 | peer | Host |
   |---|---|---|
   | ローカルの素 | `127.0.0.1` | `127.0.0.1:58889` |
   | Host を偽装 | `127.0.0.1` | `fractal2.tail73c198.ts.net` |
   | 逆に偽装 | `127.0.0.1` | `127.0.0.1:9999` |

   **peer も Host も「母艦にいること」を証明しない** — identity ヘッダを退けたのと同じ理由。
   なので承認の根拠を**合言葉の出口**に置く: デーモンは合言葉を
   **自分の stdout と `~/.kjp-edit/pair-code`（0600）にだけ**書き、
   **要求した端末には返さない**。合言葉を知れる = 母艦のコンソールか
   ホームディレクトリを読めた、なのでネットワークの偽装では越えられない
3. 🔒 **承認は capability を増やさない。** `--allow-exec` が無ければ、承認済みの端末でも実行は 403。
   承認が意味を持つのは「**この端末に、既に有効な capability を使わせてよいか**」だけ
4. 🔒 **鍵の照合は必ず `tokenWall()` を通す**（混雑の門 → 比較 → 外したら記録して遅延）。
   新しい照合経路を門の外に作らない（#63 で踏んだ形）
5. 🔒 **長寿命にするなら失効が要る。** 一覧・失効・最終使用時刻を**同じコミットで**作る
   （「緩めた守りの代わりを同じコミットで置く」）
6. ⚠️ **承認していない端末は今までどおり**（読み取りは Cookie、実行は鍵を貼る）。
   既存の経路を壊さない

## 4. 流れと門の順序

```
[端末]                          [デーモン]                     [母艦の人]
  登録したい ──POST /pair/request──▶ 読み取り認証を通す
                                    要求を1件だけ保持（TTL 5分）
                                    合言葉（ABCD-EFGH）を **stdout と 0600 のファイル**へ ──▶ 読む
                                    （応答には**合言葉を載せない**）        （serve.mjs --pair）
  合言葉を入力 ──POST /pair/claim──▶ id と合言葉を照合（tokenWall + 試行5回）
                                    一致 → 端末の鍵を**1回だけ**返す
  localStorage に保存
  以後 x-kjp-token で提示 ──────────▶ tokenWall → 実行が通る
```

**順序の理由:**

| 段 | 何を要求するか | なぜその位置か |
|---|---|---|
| 1. `/pair/request` | 読み取りの認証（既存の入口） | 誰でも要求を積めると、母艦の合言葉が上書きされ続ける（DoS） |
| 2. 合言葉の出口 | **stdout と 0600 のファイルだけ** | ここが「母艦にいること」の証明。応答に載せた瞬間に設計が崩れる |
| 3. `/pair/claim` | id + 合言葉 / **`tokenWall()`** / **試行5回** | 合言葉は 30種8文字（39.3 ビット）。記録・遅延・上限の3つで守る。上限を超えたら**要求そのものを無効**にする |
| 4. 鍵の受け取り | **1回だけ** | 再送で漏れる面を作らない（渡したら要求を閉じる） |
| 5. 端末鍵の提示 | `tokenWall()` | 総当たりに記録と遅延を付ける（#63） |
| 6. `/pair/list` `/pair/revoke` | **生の実行トークン**（端末の鍵では通さない） | 承認された端末が**他の端末を消せる／一覧できる**状態にしない |

🚨 **端末の鍵は「実行を通す」が「生トークンの払い出しは通さない」。**
`/api/v0/session` が返す生トークンは `tokenMatches()`（生の値）だけに出す。

⚠️ **HTTP 層の分界は多層防御の1枚目で、それ自体は封じ込めではない（レビュー11）。**
端末の鍵は実行を通す = 実質 RCE なので、承認された端末は
`POST /api/v0/exec argv=['cat','~/.kjp-edit/token-exec']` で**生トークンを
ディスクから直接回収できる**。つまり **exec が有効な限り、端末の鍵と生トークンは実質同等**。

🔒 **だから失効時に実行トークンを回転する（2026-08-18。利用者の判断）。**
これで**写された生トークンが死ぬ**。影響範囲:

| | 失効させたとき |
|---|---|
| 写された生トークン | 🔒 **死ぬ**（これが目的） |
| 他の承認済み端末 | ✅ **生き続ける**（端末の鍵は台帳のハッシュ照合で、生トークンとは独立） |
| 生トークンを貼ったタブ / 古い読み取り Cookie | ⚠️ 死ぬ（派生秘密が生トークン由来） |
| CLI / フック（`token-read` を読む） | ✅ **配布先を配り直すので影響なし**（`--read-secret-file`。下の 🚨） |
| **exec で仕込まれた永続化** | 🚨 **生き残る**（下の限界） |

🚨 **「失効 = 完全な封じ込め」ではない（レビュー12 で過大主張を訂正）。**
この機能が相手にするのは「**一度 exec を使った端末**」= すでに任意コード実行を得た相手で、
その相手は回転より前に **cron / 自動起動の登録 / worktree 内のフックやスクリプト /
トークンを常駐メモリに持つ別プロセス / 追加した SSH 鍵 / 監査ログの改変**を自由に仕込める。
**回転はそれらを1つも消さない。** 回転が取り消せるのは「写された生トークンで HTTP を叩く」経路だけ。
だから正確には「**失効は漏れた生トークンを無効化する。exec で確立された永続化は取り消せない**」。
⚠️ 「あの端末は切ったから安全」と読める書き方をしない（「停止しましたと言って停止していない」と同型の嘘になる）。
本当に疑わしいときは、母艦の永続化（自動起動・cron・フック）を人が確認する必要がある。

🚨 **回転時は読み取り用の派生秘密の配布先（`token-read`）も配り直す（レビュー12）。**
派生秘密は生トークン由来なので回転で変わるが、その配布先を書くのは
`scripts/serve.mjs` の**起動時1回だけ**だった。回転で更新しないと、
`scripts/precheck.mjs`（PreToolUse フック = エージェントの安全装置）が毎回死んだ値を提示して
401 → `ask` に落ち、**衝突の事前チェックがデーモンを再起動するまで黙って止まる**。
それなのに当初ここには「CLI / フック … 影響なし」と書いていた（**事実に反する記述**）。
⚠️ `serve.mjs:705` に「実測: フックが毎回 401 を受け `ask` に倒れて初めて気付いた」と
**同じ事故が別経路で記録されている** — 回転でそれを再発させていた。
サーバに `--read-secret-file` を渡し、回転時に `readSecretOf(新トークン)` を配り直す。
⚠️ 「`?token=` 付き URL を開き直せ」も復旧手段にならない（その URL の値も古い派生秘密）ので、
**新しい読み取り用 URL を stdout に出す**。

⚠️ **`--token-file` が無い構成（`--token` をリテラル）では保存先が無い**ので、
新しい値を stdout に出す（黙って in-memory だけ変えると誰も知らない値になる）。

**端末の登録は `--allow-exec` のときだけ許す**（`pairingWhy()`）。
⚠️ **この門の置き方には一度検討漏れがあった。** `--allow-write` だけの構成なら
分界は本当に効く（ファイルを読めないのでトークンを回収できない）のに、そこを閉じて
exec だけ開けていたので「**封じ込めが最も効かない構成でだけ承認できる**」逆転になっていた。
2026-08-18 に利用者と再検討し、**遠隔 exec が本命の用途**（`claude -p` をスマホから動かす）で
`--write` 層は使われないため、層を増やす代わりに**上の回転で exec 層の封じ込めを本物にする**
方針を採った。`--write` での承認が必要になったら、`list`/`revoke` を
「`--allow-write` 以上 + 生トークン」に下げれば開ける（設計は残してある）。

⚠️ **1件だけ保持する。** 承認待ちを積み上げない（積むと「どれを承認したか」が曖昧になる）。
新しい要求は古い要求を**上書きし、上書きしたことを画面に出す**。

## 5. 置き場所と記録

- `~/.kjp-edit/devices.json`（0600）。`{ id, label, secretHash, createdAt, lastUsedAt, revokedAt }`
  - 🔒 **平文の鍵を保存しない**（`sha256` を保存し、提示された値を照合する）
  - ⚠️ **Windows では `mode: 0600` はノーオペ**（Node が mode を無視する。fable の挙動検証が確認）。
    `pair-code` / `devices.json` / `token-*` が他ユーザから読めないのは、置き場所
    （`~/.kjp-edit/` = ユーザプロファイル配下）の**継承 ACL** によるものであって、
    `0600` 指定の効果ではない。**`--devices-file` を全ユーザ可読のディレクトリに置くと保護が消える**。
    「0600」という表記は POSIX での話で、Windows では**置き場所の ACL に依存する**（プラットフォームの限界）。
- 監査（`exec-audit.jsonl`）に `pair-request` / `pair-claimed` / `pair-bad-code` /
  `pair-too-many` / `pair-revoke` / `pair-first-use` を残す。**合言葉も鍵も書かない**
- `label` は端末が名乗る自由文なので**長さと文字種を縛る**（記録に自由文を入れない原則）

## 5.5 画面側の枠は3つに分ける（実装して実測で1件踏んだ）

鍵の置き場所は**3つ**あり、**強い順に選ぶ**（判定は `v0/devicekey.mjs`、テスト済み）:

| 枠 | 何が入るか | 寿命 | 他ポートから読めるか |
|---|---|---|---|
| `sessionStorage.kjp_token` | 手で貼った実行の鍵 | タブを閉じるまで | **読めない**（ポート込みオリジン単位） |
| `localStorage['kjp.device']` | 承認された端末の鍵 | 消すまで | **読めない**（同上） |
| `sessionStorage.kjp_url` | 案内 URL の `?token=` で来た値 | タブを閉じるまで | **読めない**（同上） |

強い順: **今 URL で来た鍵 > 貼った鍵 > 端末の鍵 > 前に URL で来た鍵**。

🚨 **実測で踏んだ:** 最初は `?token=` の値を**貼った鍵と同じ枠**に入れていた。
トンネル越しの URL に載るのは**読み取り専用の派生秘密**なので、それが
「貼った鍵」として端末の鍵より優先され、**承認済みの端末で
capability が「実行有効（トークン未取得）」のまま**になった。
サーバは `presented: 'device'` を返せていたので、**画面側だけの取り違え**だった。

⚠️ **「今来た」と「前に来た」を分ける理由:** URL 由来を一律で端末の鍵より下に置くと、
失効した端末の鍵を握った画面が**鍵つき URL を開き直しても死んだ鍵を送り続ける**。
今来た鍵を最優先にすることが「実行を取り戻す道」になっている。

⚠️ **書いたが削除した守り:** 「401 を受けたら端末の鍵を捨てる」。
防ぐつもりだった「死んだ鍵を握ると読み取りまで塞ぐ」は**実測で起きなかった**
（読み取りは Cookie の派生秘密で続く）。守る対象が無く、配線を測る手段も無かったので
**守りごと消した**（CLAUDE.md「測っても差が出ない守りは置かない」。`defensive` で誤魔化さない）。

## 6. 測ること（実装と同じコミットで）

- 承認前は端末の鍵が存在しないので実行は 403 のまま
- 承認後は**貼らずに**実行できる（再読込しても続く）
- 🔒 **応答に合言葉が載らない**（`/pair/request` の本文と `/pair/status` の両方）
- 🔒 **合言葉を外し続けると要求が無効になる**（5回）。無効化後は正しい合言葉でも通らない
- 🔒 **他人の id では受け取れない**（相乗りできない）
- 🔒 **読み取りの鍵だけでは `/pair/list` も `/pair/revoke` も通らない**
- 🔒 **端末の鍵では `/api/v0/session` の生トークンを取れない**（HTTP 層の分界。
  ⚠️ 上の但し書きのとおり exec で回収はできる。分界は封じ込めではなく1枚目）
- 🔒 **失効したら実行トークンが回転し、写された生トークンも死ぬ**。
  他の承認済み端末は生き続ける（端末の鍵は生トークンと独立）
- 🔒 **回転したら読み取り用の派生秘密の配布先も更新される**（フックが 401 で黙って止まらない）
  ⚠️ **exec で仕込まれた永続化は回転では消えない**（上の限界。ここを封じ込めと呼ばない）
- 端末の鍵が **`Set-Cookie` に出てこない**（字面ではなく応答で測る）
- 合言葉の照合が `tokenWall()` を通っている（記録と遅延が付く）

変異（守りを外すと落ちること）— **16件すべて KILLED を実測**
（`node scripts/mutate.mjs pair-code-in-response …`）:

| 名前 | 何を外すか | 測る検査 |
|---|---|---|
| `pair-code-in-response` | 応答に合言葉を載せる | smoke |
| `pair-no-try-limit` | 試行の上限（5回）を外す | smoke |
| `pair-id-not-checked` | id の照合を外す（相乗りできる） | smoke |
| `pair-list-accepts-device` | 端末の鍵で一覧・失効を通す | smoke |
| `pair-session-token-to-device` | 端末の鍵に生トークンを渡す（承認の連鎖） | smoke |
| `pair-secret-in-cookie` | 端末の鍵を Cookie に入れる | smoke |
| `pair-wall-bypass` | `tokenWall()` を通さない | smoke |
| `pair-require-auth-not-checked` | 壁が無い構成でも登録を許す | smoke |
| `pair-same-site-allowed` | 別ポートのページから登録できる | smoke |
| `pair-revoke-not-enforced` | 失効した端末を通す | smoke |
| `pair-list-leaks-hash` | 一覧に鍵の hash を出す | smoke |
| `pair-code-file-kept` | 使い終わった合言葉のファイルを残す | smoke |
| `pair-read-secret-beats-device` | URL の鍵を貼った鍵と同じ枠に戻す | **pair-check（実ブラウザ）** |
| `pair-ui-device-cannot-mutate` | `canMutateWith` から `device` を落とす | **pair-check（実ブラウザ）** |
| `pair-revoke-no-rotate` | 失効時に実行トークンを回転しない（写しが生き続ける） | smoke |
| `rotate-skips-read-secret` | 回転で読み取り秘密を配り直さない（フックが 401） | smoke |

🚨 **最初 3件が SURVIVED した。原因は3つとも検査側で、内容が示唆的だったので残す:**

1. `pair-code-in-response` — 母艦に出る合言葉は `ABCD-EFGH`、内部の値は**ハイフン無し**。
   そのまま `includes` していたので、**載っていても見つからなかった**
2. `pair-wall-bypass` — 「記録が残る」を経路側が書く `pair-bad-code` で見ていた。
   これは壁を外しても残るので、**壁が書く `mutation-token-failed` を見る**必要があった
3. `pair-read-secret-beats-device` — 登録成功時に古い枠を消す**後始末が不具合を隠していた**
   （枠を分ける前の移行処理。分けた後は害しかないので削除した）

## 7. これができると「プロジェクトを開く」が同じ土台に乗る

利用者の要件③（ローカルのプロジェクトを開く）は、今は**意図的に禁じている**
（「UI から任意のパスを開く経路は作らない」）。承認の仕組みができれば
「**開く = 承認つきでリポジトリを登録一覧に足す**」として同じ門に乗せられる。
先に承認を作るのはそのため。

## 8. やらないこと

- 複数ユーザ・権限分離（個人用ツール。`docs/scope.md`）
- 端末鍵の自動失効（期限）— **最終使用時刻は持つが、切るのは人の判断**。
  黙って切れると「動いていたものが動かない」になり、原因が分からない
