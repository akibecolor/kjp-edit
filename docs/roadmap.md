# ロードマップ

## Phase 0: 検証スパイク（最優先・約2週間）

**Theia を選ぶという判断は S1 と S2 の結果に依存している。**
**S1/S2 の実施手順は [spikes.md](spikes.md) に、Theia 1.74.0 のソースを読んで確定した
ファイルパス・クラス名・DIシンボル・コードスケッチ付きで書いてある。** ここでは要約だけ。

### S1 ★ゲート — シェルはレイアウト要件を満たせるか → [spikes.md](spikes.md)

**ソース調査で既に判明していること:**

| | |
|---|---|
| ○ **シェルのサブクラス化は可能** | `@theia/toolbar` が in-tree で `rebind` + `createLayout()` オーバーライドを**約95行**でやっている。全レイアウトメソッドが `protected`。呼び出し側68ファイルはトークン解決なので変更ゼロ |
| ◎ **ズーム意味論は既に実装済み** | `doToggleMaximized` が D3 ルール1（可逆なジオメトリ交換、サイズに触らない）をそのままやっている。**広げるのはゲート2つだけ** |
| × **単一ツリーに硬いブロッカー2つ** | `Area` が閉じた union（`throw` 終端・111ファイルが消費）、`LayoutData` が非対称（left/right はフラットで分割を表現できない） |
| × **focus parent は今は表現不可能** | ツリー体系が2つあり、跨ぐ共通ノード型が無い |
| 🆕 **1.74 の `PerspectiveService`** | 公式の「別の配置を得る方法」がサブクラス化から `getLayoutData()`/`setLayoutData()` の差し替えに変わった |

**残る実行時の未知（8ステップ、1〜2日）:** rebind が実際に効くか（Step 1、予想 PASS）、
サイドパネルの `multiple-document` 化がどこまで崩れるか（Step 3、**予想 PARTIAL**）、
サイドパネルへのズーム流用が `BoxLayout` で落ちるか（Step 5、**予想 FAIL、落ち方が知りたい**）、
そして **focus parent の go/no-go（Step 6）**。

**不合格なら:** dockview 7.x ベースの自作に切り替える。
その場合 Phase 1 は大幅に長くなる（エディタ・LSP・ターミナル・ツリー・
拡張ホスト・設定・キーバインド・テーマ・検索を自前で積む = 差別化機能に着手する前に6〜12ヶ月）。
**このコストを正しく認識した上で判断すること。**

### S2 ★ゲート — バックエンドを kjp-core の器にできるか → [spikes.md](spikes.md)

**ソース調査で既に判明していること:**

| | |
|---|---|
| ○ **自前エンドポイントは公式の拡張点** | `BackendApplicationContribution.configure(app)` の JSDoc が「追加のエンドポイントを提供するため」と明言。`server.setMaxListeners(0)` に「Allow any number of websocket servers」のコメント。**`@theia/ai-mcp-server` が in-tree の実証** |
| ○ **FS/ターミナル/タスクは root シングルトン** | `DiskFileSystemProvider` / `IShellTerminalServer` / `ProcessManager` / `TaskServer` は**フロントエンドがゼロでも `@inject` で直接使える**（`FileService` はフロントエンド専用） |
| ○ **ターミナル永続化は構造的に保証** | `attach(id)` + 1MB `MultiRingBuffer` でリプレイ。**`FRONTEND_CONNECTION_TIMEOUT=-1` で接続コンテキストを絶対に破棄しない**（未文書だがソースに明示） |
| × **デーモンが git を所有する経路が無い** | git は connection-scoped なプラグインホスト内の `vscode.git` のみ。バックエンドDIからもheadlessからも届かない。**自分でシェルアウトする**（元々そう決めていたので設計変更は不要） |
| △ **Electron の既存バックエンド接続は非公式だが ~15行** | フロントエンドは既に `?port=NNN` で繋いでいて fork したか知らない。`startBackend()` をオーバーライドするだけ。issue #174/#2056 は未実装のまま |
| ⚠️ **1.74 の新ゲート** | `theia-connection-token` クッキー + same-origin 検証（#17701）。ネイティブクライアントは Theia の socket.io を話せない = **自前プロトコルの実質的な論拠**。ただし自前WSは `WsRequestValidator` を完全にバイパスする = 認証は自分の責任 |
| ⚠️ **プラグインホストは接続毎** | フロントエンドが増えるたびに全VS Code拡張と言語サーバのコピーが1式増える（#10526, #6412）。**モバイルクライアントがプラグインホストを必要とする設計にしない** |

**残る実行時の未知（7ステップ、1〜2日）:**
**フロントエンドゼロでバックエンドサービスに到達できるか（Step 3 — 設計全体の要）**、そして
**⚠️ socket.io の engine.io が自前のプレーンWSを `destroyUpgrade` で殺さないか（Step 4）** —
これがソースから確定できなかった唯一の項目なので早い位置に置いてある。

**不合格なら:** kjp-core を Theia の外の独立プロセスにし、Theia backend を kjp-core の
クライアントの1つとして扱う。プロセスが2つになりサービス実装が一部重複するが、
デーモンの寿命が Theia から独立するという利点はある。

### S2b — Theia を実機のスマホで開く（10分、最大の未知が潰れる）

**問い:** 今の Theia ビルドを実機のスマホ/タブレットのブラウザで開いたとき、どこまで動くか。

**なぜ:** D5 で「モバイルにはワークベンチを載せない」と決めたが、
その判断は 2020年の Pixel 3 テストと Lumino のソース読解と meta タグの存在に基づく推論で、
**2024-2026 の実機報告が1件も見つからなかった。**
そして **Theia の AI/chat ビューは React（Monaco ではない）なので、
ワークベンチの他の部分より既に要件に近い可能性がある。**
もしAIチャットビューがスマホで十分使えるなら、セカンダリの初期版を作らずに済むかもしれない。

**やること:**
- `browser-app` を実機のスマホとタブレットで開く（iOS Safari と Chrome Android の両方）
- AIチャットビューが使えるか（これが最重要）
- Theia 1.60+ のタッチでのスプリッタドラッグとタブドラッグが実際に快適か
  （Lumino PR #123 でポインタイベント化されているのでコード上は動くはず）
- 差分ビューのスクロールと読みやすさ
- ホーム画面に追加してフルスクリーン化したときどう変わるか
  （**Theia は manifest も service worker も持たないので PWA ではない** — iOS のフルスクリーンだけ）
- 日本語IMEでの入力（Chrome Android の EditContext で改善しているはずだが未検証）

**合格基準は無い（探索的）。** 結果次第でセカンダリの優先度と初期スコープを調整する。

### S3 — Theia のコミットグラフは実用に足るか

**問い:** Theia 1.71+ の SCM History Graph は 5万コミット規模のリポジトリで
受容可能にレーンを描画するか。

**なぜ:** リリースノートで機能の存在と主張内容（DAG、レーン、ページング、
オクトパスマージ対応）は確認したが、**実際に動かしていない。**
VS Code の同等機能は issue #227475 で「数千コミットの数千変更」で無応答になることが既知。

**やること:**
- Theia IDE をインストールし、大きなリポジトリ（linux kernel / chromium / 手元のモノレポ）で開く
- レーンの見やすさ、スクロール性能、初期表示までの時間を測る
- `core.commitGraph` の有効/無効で差が出るか見る
- VS Code の組み込み Source Control Graph と並べて比較する

**合格基準:** v1 の土台として使える。改善は増分でできる。

**不合格なら:** アーキテクチャは維持したまま、グラフだけ自前実装に置き換える
（`scmHistory.ts` 移植 + 仮想化 + インターバルツリーのエッジカリング）。
これは元々 Phase 4 でやる予定の作業なので、順序が前に来るだけ。

### S4 — ACP でユーザのローカル Claude CLI を駆動できるか

**問い:** ユーザ自身の `claude` バイナリを ACP エージェントとしてサブプロセス起動し、
セッション・permission request・構造化差分を受け取れるか。

**なぜ:** これがエージェント統合の全体像。かつ**認証がユーザの手元に留まる**方式の検証
（Agent SDK を埋め込むと API キー強制になる — architecture.md の D4 参照）。

**やること:**
- ACP v1 の最小クライアントを書き、`claude` を stdio で起動して 1ターン往復させる
- permission request（承認要求）が構造化イベントとして届くか確認する
- 構造化差分（git-patch レンダリング）が取れるか確認する
- ACP Agent Registry を見て、他のエージェント（Codex CLI 等）でも同じクライアントが動くか確認する
- v2 ドラフトとの差分を評価し、機能フラグ設計の見通しを立てる

**合格基準:** 1つのACPクライアント実装で複数エージェントが動く見通しが立つ。

### S5 — 未検証項目の潰し込み（並行実施可・軽い）

## Phase 5: セカンダリクライアントとリモート強化

設計は [secondary-client.md](secondary-client.md)。

**リモート基盤:**
- デーモンを `127.0.0.1` のみにバインド（構造的な安全性）
- `tailscale serve` の統合とセットアップ導線
- OIDC（`oauth2-proxy` forward-auth）
- ケイパビリティ分離: リモートセッションから「任意シェル起動」をwithholdできる権限モデル
- 監査ログ
- 再接続の状態機械（シーケンス番号 + 有界リプレイバッファ）
- ⚠️ **モバイルの認証は WS upgrade でブラウザ供給の認証情報に依存してはいけない** —
  iPad Safari が WS upgrade に HTTP basic ヘッダを載せず Theia が固まった前例がある (theia#5810)

**セカンダリクライアント（`/m` に配信、PWA として出荷）:**
- `<details>` ベースの `type="single"` アコーディオン、全パネル lazy mount
- **Approvals / Inbox パネルを最上部固定** — 全セッション・全マシン横断の
  permission request を1リストに、各項目にセッションとマシンを表示。
  **これがクライアントの存在理由**（Happier の Inbox が唯一の良い先行例）
- 差分パネル: `@git-diff-view/react` unified モード + `diffViewWrap`。
  ファイル間スワイプとピンチズーム（Nimbalyst の2つの良いアイデア）
- ログパネル: `anser` → Reactスパン → 仮想化リスト、末尾追従。**読み取り専用、xterm.js は使わない**
- composer: テキスト、キュー済みプロンプト、画像添付、**デバイス間ドラフト同期**
- push 通知 + **プレゼンス抑制**（プライマリがフォーカス中なら鳴らさない。
  デーモンが接続状態を所有しているので誰よりも正確にできる）
- デスクトップ側ナッジ: permission プロンプトが連続したら
  「スマホから承認」を出す（Anthropic のパターン、レート制限付き）

**`/acp` エンドポイント（ACP over WebSocket）:**
既存の ACP モバイルクライアント4つ（Agmente/MIT, Ferngeist/MIT, Happy/MIT, Mobvibe/Apache-2.0）が
そのまま繋がる。**Ferngeist のドキュメントが「ほとんどの ACP エージェントは stdio しか
サポートしていない、まず WebSocket ブリッジでラップせよ」と書いている** — その穴を埋める。

**CIゲート（mux のコントリビュータガイドから採用）:**
- 全パネルを **375px 幅**で検証
- パネル内部は**ビューポートのメディアクエリではなく CSS `@container` クエリ**でサイズ指定
  （同じカードがデスクトップのサイドバーでもスマホのスタックでも正しく描画される）
- Storybook のビューポートを **390 / 744 / 1200 / 1900** に固定
- グリッドセルは `minmax(0,1fr)`

**明示的に作らないもの:** side-by-side 差分、コードエディタ、インタラクティブなターミナル、
**コミットグラフ**（調査した全ツールでモバイルにグラフを出しているものはゼロ）。

**完了条件:** 外出先のタブレットから、家のマシンで走っているエージェントの進捗を見て、
差分をレビューして、承認できる。ターミナル権限は明示的に付与しない限り無い。

## Phase 6: ビューアパネル

設計は [viewer.md](viewer.md)。

**⚠️ Markdown ビューアは Phase 3 に前倒しすべき。** エージェントを走らせ始めた瞬間から
設計文書・計画・レポートが Markdown で*ストリームされて*くるので、
それを読む手段が無いとエージェント統合が完成しない。
残りのビューアは Phase 6 でよい。

**Markdown（Phase 3 と同時）:**
- **Streamdown (Apache-2.0)** をレンダラに。ストリーミング・未完成markdown処理・
  `rehype-harden`・KaTeX・Shiki・Mermaid の配線が1依存で入る
- **サンドボックス化された別オリジンのフレームで描画し、すべてサニタイズする**
  （エージェント出力は半信頼。プロンプトインジェクションで `<img onerror=…>` が来る）
- **`DiagramRenderer` インタフェースを最初から切る** — クライアント側 mermaid (v1) と
  デーモン側 Kroki (v2) の2実装、共通のコンテンツハッシュSVGキャッシュ。
  **クライアント側 mermaid を直結するとセカンダリのバンドルが維持不能になった時点で書き直しになる**
- Shiki の代わりに **Monaco のトークナイザ再利用**をプロトタイプする（追加約0KB、
  プレビューの色がエディタと完全一致）。先行事例が無いのでアイデア段階
- `.excalidraw` パネル（**Excalidraw は MIT**）— 安く、効果が高く、エージェントが編集可能な図を書ける

**ブラウザパネル（Phase 6）:**
- 通常の Theia `ReactWidget` 内の **`<iframe>`**。`persist:preview` パーティションで
  `X-Frame-Options` と CSP `frame-ancestors` を除去（**アプリ全体では絶対にやらない**）
- **プレビューは別オリジン/サブドメインから配信する。交渉不可**
  （Theia mini-browser の RCE アドバイザリが教訓）
- **Eruda (MIT)** を注入して devtools パネル。デバイス「エミュレーション」はCSS 3サイズ
  （desktop / 390×844 / ドラッグ可能）。**Vibe Kanban の実体がこれで、CDPではない**
- 自前の要素ピッカー（~300行）: shadow-DOM オーバーレイ、`elementFromPoint`、
  `{selector, outerHTML, computedStyles, boundingRect, screenshotDataURL, __source?}` →
  エージェントの文脈へ。**stagewise は AGPLv3 なので採用しない**

**その他のビューア（Phase 6、全部安い）:**
- 画像/SVG（**SVG は `<script>` を運べるのでサンドボックスかDOMPurify**）
- HTML → ブラウザパネルに流すだけ
- ログ → xterm.js（デスクトップのみ。**必ず仮想化する**）
- **CSV/Parquet/SQL → hyparquet + HighTable + squirreling（全部MIT、合計 ~50KB gz）**

**後回し:** PDF（pdfjs-dist は展開69MB、モバイルで悪い）、Jupyter、WYSIWYG編集
（**分割ペインプレビューの方がむしろ良い** — WYSIWYG→markdown の直列化が
エージェントの編集に対してノイズだらけの diff を生む）。**tldraw は永久に使わない**（プロプライエタリ）。

**Phase 7 候補（差別化要素）:** 人間とエージェントで**1つのブラウザを共有**する。
エージェントが人間のログイン済みセッションを継承するので「エージェントが認証壁を越えられない」問題が消える。
`connectOverCDP` で技術的には踏み固められているが、**OSSでやっているプロジェクトが無い。**
危険が2つ: 同じタブの取り合い（→エージェントに専用ターゲットを与え人間が adopt する）と、
クッキージャー共有がプロンプトインジェクションの増幅器になること（→プロジェクト単位の明示的オプトイン）。
