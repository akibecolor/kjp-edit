# ロードマップ

## Phase 0: 検証スパイク（最優先・約2週間）

**Theia を選ぶという判断は、以下4つのスパイクの結果に依存している。**
どれもコードを1行も書く前に潰しておくべきリスクで、いずれも1〜2日。
**S1 と S2 が go/no-go ゲート。**

### S1 ★ゲート — Theia のシェルはレイアウト要件を満たせるか

**問い:** `ApplicationShell` をサブクラス化して、left/right サイドエリアも
`TheiaDockPanel` の `'multiple-document'` モードにし、**すべてのパネルを単一の
コンテナツリーに入れる**ことができるか。何行の改変で済むか。

**なぜ最優先か:** レイアウトが本プロジェクトの第一の差別化要素。
ここで Theia が抵抗するなら、主要機能をブロックするベースを選んだことになる。

**やること:**
- `theia-blueprint` をクローンしてビルドし、`ApplicationShell` /
  `TheiaDockPanel` / `ViewContainer` の構造を読む
- DI で `ApplicationShell` を rebind し、左右エリアを分割可能にする最小の変更を試す
- ファイルツリーとコミットグラフを main エリアの任意タイルに置けるか確認する
- `zoomedNodeId` 方式のズームを Lumino の上に載せられるか確認する
  （Lumino は maximize を持たないので自前実装になる）
- `focus parent` に相当する操作が Lumino のツリーAPIで表現できるか確認する

**合格基準:** 左右エリアの分割が現実的な改変量（数百行以内、コアのフォーク不要）で達成でき、
かつ D3 のルール1〜5 を実装する見通しが立つ。

**不合格なら:** dockview 7.x ベースの自作に切り替える。
その場合 Phase 1 は大幅に長くなる（エディタ・LSP・ターミナル・ツリー・
拡張ホスト・設定・キーバインド・テーマ・検索を自前で積む = 差別化機能に着手する前に6〜12ヶ月）。
**このコストを正しく認識した上で判断すること。**

### S2 ★ゲート — Theia のバックエンドを kjp-core の器にできるか

**問い:** Theia backend 拡張として**自前のバージョン付き WS/HTTP エンドポイント**を公開し、
その内部で Theia の注入済みサービス（`FileService`、terminal、SCM、task）を Inversify DI で
消費できるか。そしてその1つのバックエンドが、Theia ワークベンチのクライアントと
自前のモバイルクライアントを**同時に**賄えるか。

**なぜこの形か（前回の設計からの変更）:** [architecture.md](architecture.md) の
D1 訂正と D5 の通り、**Theia のフロントエンド↔バックエンドプロトコルは手書きクライアントから
使ってはいけない**（socket.io + 独自チャネルフレーミング、1.27 で全面書き直しの前例、
バージョニング無し、両端 Inversify 前提）。Theia 自身のドキュメントが
「バックエンドは自分のエンドポイントを登録・公開できる」と正解を示している。

**やること:**
- `theia-blueprint` の `browser-app` を `:3000` で起動し、まず2つのブラウザタブから同時に開いて
  ファイル編集・ターミナル・git 操作が両タブでどう見えるか観察する
  （特に: 一方でファイルを保存したとき他方はどうなるか）
- **backend 拡張を1つ書き、`/api/v0/ping` のような自前エンドポイントを立てる。**
  そこから `FileService` を DI で取得してファイル一覧を返せるか確認する
- **`@theia/plugin-ext-headless` を確認する。** ここのプラグインは
  フロントエンド接続毎にホストを起こす `@theia/plugin-ext` と違って
  **全フロントエンドで共有される1つのバックエンドホストプロセスに住む** — まさに必要なスコープ。
  公式の意図も「サービスが全接続フロントエンドで共有される、あるいはCLIのような
  ヘッドレスシナリオに供する場合」と書かれている。実際にそう動くか確かめる
- `@theia/terminal` のターミナルがサーバ側で永続し再アタッチできるか確認する
- Electron アプリを既存の browser バックエンドに向けられるか試す
  （**Electron ターゲットは自身のバックエンドをエフェメラルな localhost ポートで起動するので、
  これは文書化された経路ではない**）
- レイアウト状態がどこに保存されているか確認する（localStorage = クライアント毎。
  D2/D5 の「レイアウトは共有しない」方針と一致するので**望ましい**）

**合格基準:** 自前エンドポイントから Theia のサービスに到達でき、
2クライアントが同一バックエンドに同時接続でき、ターミナルが再アタッチ可能。

**不合格なら:** kjp-core を Theia の外の独立プロセスにし、Theia backend を kjp-core の
クライアントの1つとして扱う。プロセスが2つになりサービス実装が一部重複するが、
デーモンの寿命が Theia から独立するという利点はある。

### S2b — Theia を実機のスマホで開く（10分、最大の未知が潰れる）

**問い:** 今の Theia ビルドを実機のスマホ/タブレットのブラウザで開いたとき、どこまで動くか。

**なぜ:** D5 で「モバイルにはワークベンチを載せない」と決めたが、
その判断は 2020年の Pixel 3 テストと Lumino のソース読解と meta タグの存在に基づく推論で、
**2024-2026 の実機報告が1件も見つからなかった。**
そして **Theia の AI/chat ビューは React（Monaco ではない）なので、
ワークベンチの他の部分より既に要件に近い可能性がある。**
もしAIチャットビューがスマホで十分使えるなら、セカンダリの初期版を作らずに済むかもしれない。

**やること:**
- `browser-app` を実機のスマホとタブレットで開く（iOS Safari と Chrome Android の両方）
- AIチャットビューが使えるか（これが最重要）
- Theia 1.60+ のタッチでのスプリッタドラッグとタブドラッグが実際に快適か
  （Lumino PR #123 でポインタイベント化されているのでコード上は動くはず）
- 差分ビューのスクロールと読みやすさ
- ホーム画面に追加してフルスクリーン化したときどう変わるか
  （**Theia は manifest も service worker も持たないので PWA ではない** — iOS のフルスクリーンだけ）
- 日本語IMEでの入力（Chrome Android の EditContext で改善しているはずだが未検証）

**合格基準は無い（探索的）。** 結果次第でセカンダリの優先度と初期スコープを調整する。

### S3 — Theia のコミットグラフは実用に足るか

**問い:** Theia 1.71+ の SCM History Graph は 5万コミット規模のリポジトリで
受容可能にレーンを描画するか。

**なぜ:** リリースノートで機能の存在と主張内容（DAG、レーン、ページング、
オクトパスマージ対応）は確認したが、**実際に動かしていない。**
VS Code の同等機能は issue #227475 で「数千コミットの数千変更」で無応答になることが既知。

**やること:**
- Theia IDE をインストールし、大きなリポジトリ（linux kernel / chromium / 手元のモノレポ）で開く
- レーンの見やすさ、スクロール性能、初期表示までの時間を測る
- `core.commitGraph` の有効/無効で差が出るか見る
- VS Code の組み込み Source Control Graph と並べて比較する

**合格基準:** v1 の土台として使える。改善は増分でできる。

**不合格なら:** アーキテクチャは維持したまま、グラフだけ自前実装に置き換える
（`scmHistory.ts` 移植 + 仮想化 + インターバルツリーのエッジカリング）。
これは元々 Phase 4 でやる予定の作業なので、順序が前に来るだけ。

### S4 — ACP でユーザのローカル Claude CLI を駆動できるか

**問い:** ユーザ自身の `claude` バイナリを ACP エージェントとしてサブプロセス起動し、
セッション・permission request・構造化差分を受け取れるか。

**なぜ:** これがエージェント統合の全体像。かつ**認証がユーザの手元に留まる**方式の検証
（Agent SDK を埋め込むと API キー強制になる — architecture.md の D4 参照）。

**やること:**
- ACP v1 の最小クライアントを書き、`claude` を stdio で起動して 1ターン往復させる
- permission request（承認要求）が構造化イベントとして届くか確認する
- 構造化差分（git-patch レンダリング）が取れるか確認する
- ACP Agent Registry を見て、他のエージェント（Codex CLI 等）でも同じクライアントが動くか確認する
- v2 ドラフトとの差分を評価し、機能フラグ設計の見通しを立てる

**合格基準:** 1つのACPクライアント実装で複数エージェントが動く見通しが立つ。

### S5 — 未検証項目の潰し込み（並行実施可・軽い）

research.md の「未検証・要確認」表を消化する。特に重要なもの:

- **Nimbalyst の「git log視覚拡張」と mux の「git divergence UI」を実際に触る。**
  → G1（コミットグラフ中心の履歴編集UIが空白）という前提の検証。
  もしどちらかが既に Sublime Merge 級なら、差別化の軸を再考する必要がある
- `theia-blueprint` の `electron-app/package.json` の実際の依存を読む（AI機能の有無）
- dockview の `LICENCE.md` 実文を読む
- EPL-2.0 の義務範囲を確認（法務相談が必要なら早めに）

## Phase 1: 土台（S1/S2 通過後）

- `theia-blueprint` をベースに `kjp-edit` としてブランディング（商標: 製品名に「Theia」を含めない）
- browser ターゲットと electron ターゲットの両方をビルド・起動できる状態にする
- 拡張機能レジストリを **Open VSX** に向ける（MSマーケットプレイスはToS違反）
- CI: 3プラットフォームのビルドとインストーラ生成
- ライセンスを確定して `LICENSE` を置く（EPL-2.0 との整合を確認）

**完了条件:** 自分のマシンでデスクトップアプリとして起動し、同時に別端末のブラウザから
同じバックエンドに繋がる。

## Phase 2: レイアウト — 差別化その1

architecture.md D3 の実装。

- `ApplicationShell` サブクラス化で単一コンテナツリーを実現（S1の成果を製品化）
- `zoomedNodeId` 方式のズーム（ルール1〜4）
- `focus parent` / `focus child`（ルール5）
- i3/tmux 由来のキーボードコマンド一式
- Zellij 風の常時表示キーバインドバー
- レイアウトのJSON直列化とクライアント毎の永続化

**完了条件:** Zed の issue リスト（#21776, #47207, #32715, #52584, #27237）に相当する
状況を手で再現して、どれも起こらないことを確認する。**これが受け入れテスト。**

## Phase 3: エージェントオーケストレーション

- worktree レジストリ（デーモン所有、排他ロック付き）
- ACP クライアント（v1、v2は機能フラグ）
- エージェントセッションをレイアウトツリーの第一級 `panelType` として扱う
- permission / 承認UI
- 長寿命セッションを tmux/abduco でバックし、アプリ終了を生き残らせる

**完了条件:** 3エージェントを別worktreeで並列に走らせ、アプリを再起動しても
セッションが生きている。

## Phase 4: コミットグラフと履歴編集 — 差別化その2（最大の空白）

- グラフバックエンド: `git log --topo-order` ストリーミング + `core.commitGraph`
- レーン割当: `scmHistory.ts` (MIT) 移植 → pvigier straight-branches に発展
- 描画: 行仮想化 + インターバルツリーのエッジカリング（180倍の効果）
- **履歴編集UI**: interactive rebase / 並べ替え / squash / コミット分割 /
  過去へのfixup / worktree間cherry-pick / reflog救出
- **クロスエージェントレビュー**（G4）: 全ブランチを1枚のグラフに描き、
  ファイル衝突とマージ順序を可視化

**完了条件:** 「40個の『fix tests』コミットを3つのレビュー可能なコミットに整形する」を
グラフ上の操作だけで完遂できる。

## Phase 5: セカンダリクライアントとリモート強化

設計は [secondary-client.md](secondary-client.md)。

**リモート基盤:**
- デーモンを `127.0.0.1` のみにバインド（構造的な安全性）
- `tailscale serve` の統合とセットアップ導線
- OIDC（`oauth2-proxy` forward-auth）
- ケイパビリティ分離: リモートセッションから「任意シェル起動」をwithholdできる権限モデル
- 監査ログ
- 再接続の状態機械（シーケンス番号 + 有界リプレイバッファ）
- ⚠️ **モバイルの認証は WS upgrade でブラウザ供給の認証情報に依存してはいけない** —
  iPad Safari が WS upgrade に HTTP basic ヘッダを載せず Theia が固まった前例がある (theia#5810)

**セカンダリクライアント（`/m` に配信、PWA として出荷）:**
- `<details>` ベースの `type="single"` アコーディオン、全パネル lazy mount
- **Approvals / Inbox パネルを最上部固定** — 全セッション・全マシン横断の
  permission request を1リストに、各項目にセッションとマシンを表示。
  **これがクライアントの存在理由**（Happier の Inbox が唯一の良い先行例）
- 差分パネル: `@git-diff-view/react` unified モード + `diffViewWrap`。
  ファイル間スワイプとピンチズーム（Nimbalyst の2つの良いアイデア）
- ログパネル: `anser` → Reactスパン → 仮想化リスト、末尾追従。**読み取り専用、xterm.js は使わない**
- composer: テキスト、キュー済みプロンプト、画像添付、**デバイス間ドラフト同期**
- push 通知 + **プレゼンス抑制**（プライマリがフォーカス中なら鳴らさない。
  デーモンが接続状態を所有しているので誰よりも正確にできる）
- デスクトップ側ナッジ: permission プロンプトが連続したら
  「スマホから承認」を出す（Anthropic のパターン、レート制限付き）

**`/acp` エンドポイント（ACP over WebSocket）:**
既存の ACP モバイルクライアント4つ（Agmente/MIT, Ferngeist/MIT, Happy/MIT, Mobvibe/Apache-2.0）が
そのまま繋がる。**Ferngeist のドキュメントが「ほとんどの ACP エージェントは stdio しか
サポートしていない、まず WebSocket ブリッジでラップせよ」と書いている** — その穴を埋める。

**CIゲート（mux のコントリビュータガイドから採用）:**
- 全パネルを **375px 幅**で検証
- パネル内部は**ビューポートのメディアクエリではなく CSS `@container` クエリ**でサイズ指定
  （同じカードがデスクトップのサイドバーでもスマホのスタックでも正しく描画される）
- Storybook のビューポートを **390 / 744 / 1200 / 1900** に固定
- グリッドセルは `minmax(0,1fr)`

**明示的に作らないもの:** side-by-side 差分、コードエディタ、インタラクティブなターミナル、
**コミットグラフ**（調査した全ツールでモバイルにグラフを出しているものはゼロ）。

**完了条件:** 外出先のタブレットから、家のマシンで走っているエージェントの進捗を見て、
差分をレビューして、承認できる。ターミナル権限は明示的に付与しない限り無い。

|---|---|
| **カテゴリの淘汰** | 8ヶ月で Crystal 廃止・Terragon 停止・Vibe Kanban 廃業・Sketch archived・Omnara 方式転換。「単独のオーケストレーションはビジネスにならない」。OSS・ローカルファーストで、CLIベンダが出荷しないもの（= 履歴編集UI）で差別化する方針はこの淘汰への回答になっている |

| **Monaco とモバイル** | architecture.md の未解決点。セカンダリの想定端末を明示的に決め、drift で決めない |
| **フォーク保守税** | Theia を選ぶ理由の大半がこれの回避（加算的npm拡張 vs パッチ列）。この優位を捨てる変更（コアのフォーク）は毎回コストを意識して判断する |
