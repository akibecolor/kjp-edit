# ホスティング設計（Cloudflare 前提の調査結果）

2026-08-01 時点。Cloudflare の公式ドキュメント・limits・pricing・法務ページを直接取得して確認。

## 結論: 4段のはしごにする。既定は最下段で、上は全部オプトイン

そして**最重要の発見: リレーを「我々が運営する」のではなく
「ユーザ自身の無料 Cloudflare アカウントにワンクリックでデプロイさせる」ことで、
[review-findings.md](review-findings.md) #7 の D7 矛盾が解ける。**

| 段 | 内容 | 必要なアカウント | 費用 |
|---|---|---|---|
| **Tier 0**（既定） | デーモンは `127.0.0.1`、デスクトップは loopback。LANアクセスは best-effort | **なし** | $0 |
| **Tier 1** | 「自分でトンネルを持ってくる」— `cloudflared` / Tailscale Funnel / `ssh -R` / frp / rathole / chisel を文書化するだけ | 各サービス | — |
| **Tier 2** ⭐推奨 | **~200行の Worker + Durable Object を、ユーザ自身の無料 Cloudflare アカウントにワンクリックデプロイ。暗号文のみを転送** | **Cloudflare（ユーザ自身の。ドメイン不要・支払い情報不要）** | **$0** |
| **Tier 3** | 我々が運営するリレー。アカウントを一切作りたくない人向けの利便性。レート制限付き・best-effort と明示 | なし | 〜$5/月 |

**Tier 2 が調査全体で最も良い適合。** NAT越えとブラウザの secure context を同時に解決し、
費用ゼロで、**我々もCloudflareも信頼経路から外れる。**

## 1. そもそも何をホストする必要があるか

| | 本当に必要か | Cloudflare に良いプリミティブがあるか |
|---|---|---|
| **暗号化リレー / ランデブー** | **オプトインのリモート経路のみ** | **ある — Workers + Durable Objects。この一覧で最良の適合** |
| Webサイト / ドキュメント | ○ | ○ Pages か Workers Static Assets。コモディティなので GitHub Pages でも同じ |
| リリース / インストーラ配布 | ○ | R2 でも動くが、**OSSなら GitHub Releases が既定として優れている**（§5） |
| **更新チェックエンドポイント** | **× 配布に畳める** | 同じホスト上の静的 `latest.yml`。**サービスを作らない** |
| **ペアリング / QRブローカー** | **× 設計上の罠** | **不要。** QRに秘密を直接載せてデバイス同士で PAKE させる。**ペアリングコードを発行するブローカーは RCE 経路上の信頼される第三者になる。** リレーのランデブーIDで足りる |
| 将来の有料ホスト版 | 今は不要 | Workers/DO で担えるが §3 の転売条項に注意 |

**(d) と (e) を設計で回避できるのは費用の話ではなくセキュリティの勝ち。**

## 2. Cloudflare Tunnel (`cloudflared`)

- **ライセンス: Apache-2.0**。**コントロールプレーンはセルフホスト不可**（想定通り）
- **Cloudflare アカウントが必要。** README が今も「サイトを Cloudflare アカウントに追加する必要がある」と明記
- **公開ホスト名付きの named tunnel には**ドメインも必要。Access 保護アプリはホスト名が
  「アカウント内のアクティブなゾーン」である必要があり、partial/CNAME 設定は **Business プラン**。
  現実的には「ドメインを持ってネームサーバを Cloudflare に委譲」
- Tunnel 自体は無料で有料 Access シートも不要。上限は 1,000 tunnels/account、25 replicas/tunnel

### ⚠️ Quick tunnels (`trycloudflare.com`) — 決定的な発見

**アカウントもドメインも不要。Cloudflare で唯一の真にアカウントレスな経路。** しかし:

- **ハード上限: in-flight 200リクエスト**
- **Server-Sent Events 非対応** → SSE を WebSocket のフォールバックにできない
- 「テストと開発専用」「SLAも稼働率も保証しない」
- **実行ごとにランダムなサブドメイン** — URLが再起動で変わる
- **そして Access で保護できない**（Access アプリは*自分の*ゾーンのホスト名を要求し、
  ホスト名は実行毎にランダム割り当てなので事前宣言できない）

**→ Cloudflare で唯一のゼロサインアップ経路は、推測可能なURL上の
「認証なしで公開到達可能な RCE エンドポイント」を作る。サポート経路として出荷しない。**

### TLS 終端

**Cloudflare はエッジで TLS を終端し平文を見られる。**
Flexible / Full / Full(strict) のどれも「訪問者↔Cloudflare」「Cloudflare↔オリジン」の
2接続として記述されており、**プロキシされるモードで Cloudflare が終端しないものは存在しない。**

**アプリ層 E2E がこれを完全に変える。ここが設計の急所。**
WebSocket のペイロードがデーモン↔スマホ間で既に封印されていれば（Noise/libsodium）、
Cloudflare が見るのは暗号文とメタデータ（タイミング・サイズ・ランデブーID）だけ。
**Cloudflare が「信頼されないバイトパイプ」になる — ターミナル+エージェントの
エンドポイントに対して唯一擁護できる姿勢。初日からこれを前提に設計し、
CF の TLS をセキュリティ境界として扱わない。**

### ToS / AUP

- **歴史的な §2.8「非HTML禁止」条項は消えている。** 制約は
  [Application Services 個別条項](https://www.cloudflare.com/service-specific-terms-application-services/)に**移動**し、
  「Enterprise でない限り、動画やその他の大きなファイルを CDN 経由で配信するには
  特定の有料サービス（**Developer Platform**、Images、Stream）を使う必要がある」。
  **カーブアウトが Developer Platform を名指ししているので Workers/DO リレーは正しい側。**
  無料ゾーン経由の `cloudflared` トンネルは明白に免除されておらず、
  大きなリポジトリのクローンやビルド成果物を通すのは議論の余地あり
- **⚠️ §2.2.1(j): 「Services を使って VPN またはその他類似のプロキシサービスを提供してはならない」** —
  リレーにとって最も関連が深く、かつ**本当に曖昧**。Cloudflare One のカーブアウトは無い
- **§2.7 の Acceptable Use は一般的（マルウェア・フィッシング・違法コンテンツ）。
  リモートシェルを禁止する条項は無い。** Cloudflare 自身が SSH-over-Tunnel を文書化し、
  ブラウザ描画の SSH/VNC を機能として出荷している
- **長寿命 WebSocket の禁止も無い。**「WebSockets は全プランでサポートされる」
- **[Developer Platform 個別条項](https://www.cloudflare.com/service-specific-terms-developer-platform/)は
  「End Users」への提供を明示的に想定し、プロキシ/リレー禁止条項が無い。**
  これが §2.2.1(j) の懸念を CDN ゾーンのトンネルに比べて実質的に緩和する
- **Zero Trust 個別条項は転売を禁止**（ASP・マネージドセキュリティ・アウトソーシング・
  タイムシェアリング・サービスビューロー関係）

## 3. Workers + Durable Objects を専用の暗号化リレーにする

**最強の選択肢で、我々の要件には Tunnel より適合が良い。**

### WebSocket Hibernation API

`ws.accept()` ではなく **`ctx.acceptWebSocket(server)`** を使い、
`addEventListener` ではなくハンドラ*メソッド*（`webSocketMessage` / `webSocketClose` /
`webSocketError`）を使う。すると:

- **クライアントは Cloudflare のエッジに接続したまま、DO はメモリから追い出される**
- **メモリ内状態は破棄される。** 次のイベントでコンストラクタが再実行されるので**コンストラクタは軽くする**
- 接続毎の状態は `serializeAttachment()` / `deserializeAttachment()` で生存（**接続あたり最大 16,384 バイト**）
- **費用上の意味: 「Billable Duration (GB-s) はハイバネーション中には発生しない」**
- WebSocket プロトコルの ping フレームは自動応答され、**ハイバネーションを中断しない**
- 🎯 **`setWebSocketAutoResponse()`** — *アプリケーション層*のキープアライブ用。
  「**ハイバネーション中の WebSocket を起こさず、課金対象の duration を発生させずに**
  自動応答が返される」。リクエスト/レスポンスは 2,048 文字まで。
  **これを使うこと。素朴なアプリ層ハートビートはハイバネーションを完全に無効化してしまう**

### ハード上限

| 項目 | 値 |
|---|---|
| DO あたりの同時 WebSocket 数 | **⚠️ 未文書。**「インスタンスあたり数千クライアント」としか書かれていない（よく引用される 32,768 は現在ドキュメントに無い） |
| WebSocket メッセージサイズ | **32 MiB**（受信のみ） |
| 最大接続時間 | **⚠️ 未文書。** 呼び出し側が接続している間 wall time は無制限 |
| リクエストあたり CPU | 既定30秒、5分まで設定可（WebSocket メッセージも数える） |
| DO あたりリクエスト | ソフト上限 **1,000/秒**。超えると *overloaded* を返す |
| 同時アウトバウンド接続 | リクエストあたり **6** |
| DO あたりストレージ (SQLite) | 10 GB、key+value 合計 ≤ 2 MB |
| ハイバネーション発火 | **非アクティブ10秒**（`setTimeout`/`setInterval`・in-flight `fetch()`・標準API WebSocket・TCP/アウトバウンドWSが無い場合） |
| 完全 eviction（非ハイバネート可） | 非アクティブ **70〜140秒** |
| アウトバウンド WebSocket | ハイバネーションを阻害し、**接続あたり最大15分**しか DO を生かさない |

**接続中の eviction: あり。**「シャットダウン中に WebSocket リクエストは自動的に終了される」。
ストレージは残るがメモリ内状態は残らない。

### 🚨 運用上の地雷

> **「コード更新は全 WebSocket を切断する。新バージョンのデプロイは全 Durable Object を
> 再起動し、既存の接続を切断する。」**

**リレーをデプロイするたびに全アクティブセッションが落ちる。**
**再接続+リジューム（resume）はオプションではなく必須のプロトコルプリミティブ。**
（[architecture.md](architecture.md) D1 の4番目「再接続は第一級の状態機械」がここで報われる。）

### 費用（50ユーザ、1端末が1日数時間・大半アイドル）

- Workers Paid: **最低 $5/月**（1000万リクエスト + 3000万 CPU-ms 込み）
- DO リクエスト: 100万/月込み、以降 $0.15/M。**受信 WebSocket メッセージには 20:1 の割引**
  （「WebSocket 受信100メッセージが5リクエストとして課金される」）
- DO duration: **400,000 GB-s/月込み**、以降 $12.50/M GB-s（DOあたり 128MB 前提）

| プロファイル | 課金対象DOリクエスト/月 | GB-s/月 | 月額 |
|---|---|---|---|
| 大半アイドル（実トラフィック 1日20分程度） | 〜0.9M（込みの1M以内） | 〜225k（込みの400k以内） | **$5**（基本料のみ） |
| ヘビー（1日3時間の連続ストリーミング） | 〜24M → 超過 $3.50 | 〜2.0M → 超過 $20 | **〜$29** |

**支配するのはリクエストではなく duration。** メッセージが流れ続ける DO は
10秒のハイバネーション閾値に到達しない。

🎯 **重要な系: 1ユーザ分のリレーは無料プランに余裕で収まる**
（13,000 GB-s/日 ≒ 128MB オブジェクト1つが1日29時間起きていられる）。
**つまり各ユーザが自分の無料アカウントにデプロイして $0。これが Tier 2 の根拠。**

### レイテンシと配置

- **DO は最初の `get()` の近くに作られ、配置は作成時に固定される** —
  「Durable Objects は作成後に配置を変えない」
- `locationHint` に **`apac-ne`**（他に `apac`, `apac-se`, `wnam`, `enam`, `weur` 等）。
  ただしベストエフォート。Jurisdiction（`eu`/`us`/`fedramp`）は硬い境界だが日本の選択肢は無い

**日本の開発者 + 米国で作られた DO = スマホ(JP)→US→デーモン(JP) で
往復に約 +220〜300ms 追加。ターミナルのキーストロークエコーが壊れて感じる。**

**対処2つ:** (1) `locationHint: "apac-ne"` を渡す、
(2) 🎯 **DO を作るのはスマホではなくデーモンにする** —
デーモンの位置は安定していて開発者と同じ場所だが、**スマホはどこにでも移動しうる。**
配置が作成時固定であることから直接導かれる設計制約。

### Worker からデーモンへダイヤルアウトできるか → **できない**（想定通り）

理由が2つ独立にある:
1. **ネットワークトポロジで決まる。** デーモンは NAT 背後の `127.0.0.1` にバインドする。
   インターネットから誰もダイヤルインできない
2. **できたとしても経済的に間違い。** DO からのアウトバウンド WebSocket は
   **ハイバネーションを阻害し最大15分**。素の Worker はリクエストスコープで
   リクエスト間の接続を保持できない

**→ デーモンとスマホの両方が DO に*インバウンド*で WebSocket クライアントとして繋ぐ。
DO は純粋にサーバで、両接続がハイバネート可能、アイドル費用ゼロ。これが正しい形。**

## 4. 代替案 — ユーザは誰のアカウントが必要か

| | アカウント必要? | 誰の | コントロールプレーンをセルフホスト可? | ブラウザだけのスマホで届く? |
|---|---|---|---|---|
| **Tailscale Funnel** | **○** | **SSO IdP**（Google/GitHub/Apple/MS/Okta/OIDC/passkey） | × | **○** |
| Tailscale Serve | ○ | 同上 | × | **× スマホに Tailscale を入れて tailnet に参加させる必要がある** |
| **Headscale** | 第三者は不要 | — | **○** | **× Funnel 相当が無い** |
| VPS + frp / rathole / chisel / `ssh -R` | **○** | VPS事業者（+支払い手段） | ○ | ○ |
| WebRTC + 公開STUN | **STUNは不要** | — | signaling は自分で用意 | ○ |
| …TURN フォールバック込み | **○** | TURN事業者 | ○ (coturn) | — |
| iroh + n0 relays | **○ 不要**（無料・アカウント不要・APIキー不要） | — | ○ | **⚠️ ブラウザ/WASM 対応が未確認 — 設計上致命的** |
| LAN のみ + mkcert | **不要** | — | — | **○ ただし CA 信頼の手順が必要** |
| CF quick tunnel | **不要** | — | × | ○（だが上記の通り出荷不可） |

**計算を変える3つの発見:**

1. 🚨 **Tailscale はメールアドレスでサインアップできない。**
   公式KB: 「Tailscale はメールアドレスでのサインアップをサポートしていない」。
   **つまり Cloudflare より*厳しい*サインアップで、緩いのではない。**
   無料 Personal プランは無制限デバイス・**6ユーザ**。コーディネーションサーバはプロプライエタリ。
   Funnel はポート **443/8443/10000** 限定で**帯域上限は非開示**、
   WebSocket 対応はコミュニティ検証のみでベンダ文書化されていない
2. **Headscale には Funnel 相当が無く、今後も作られない**
   （issue #1040 が "not planned" でクローズ、features.md で `Funnel`/`Serve` 未チェック）。
   **セルフホストのコントロールプレーンは得られるが公開イングレスが無い**ので
   スマホにクライアントを入れる必要がある。しかも公開IPのホストが別途必要。まだ v0.29.x
3. **「VPS」は摩擦の低い選択肢ではない。** 支払い手段・DNS・TLS・systemd・
   ファイアウォール設定が必要で、「GitHubでサインイン」を押すより厳密に難しい

## 5. 静的ホスティングと配布 — ⚠️ 部分的に未検証

自分で確認できたこと:
- **Workers には無料の `*.workers.dev` サブドメインが付き、独自ドメインは不要。**
  ただし「無料サイトとして扱われ、業務上重要でない個人/趣味プロジェクト向け」
  「本番の Worker は Workers route か独自ドメインで動かすことを推奨」
- **CDN の大きいファイル条項が Developer Platform（R2を含む）を認可された経路として名指し**
  しているので、**契約上インストーラの置き場は R2 が正しい**（無料 CDN ゾーンとは違う）

**⚠️ 未検証で、コミット前に確認が必要**（推測であり依拠してはいけない）:
R2 のエグレス無料、Pages のファイルあたり ~25 MiB 上限、
Pages が Workers Static Assets に対して legacy 化しているか、
R2 の 5 GiB 単一PUT/マルチパート上限、R2 の Range リクエスト対応、
`r2.dev` のレート制限、GitHub Releases のアセットあたり ~2 GiB 上限と帯域ポリシー、
**そして GitHub Releases が Range リクエストをサポートするか**
（`objects.githubusercontent.com` へのリダイレクトが electron-updater の
差分ダウンロードを壊すという報告が長年ある）。

**それでも推奨は変わらない: バイナリの主ホストは GitHub Releases。**
OSSなら無料・実質無制限・`electron-updater` の一級プロバイダサポートあり・
我々のアカウントもインフラも不要で、**Cloudflare の面積をゼロに保てる。**
**差分更新に依拠する前に Range リクエストの件を確認すること。**
失敗するなら R2 にミラーして更新フィードをそちらに向ける。
`latest.yml` の Cache-Control はどのCDNでも明示的な注意が必要 — 古い更新マニフェストは嫌な失敗モード。

## 6. Cloudflare Zero Trust / Access

- **必要なもの:** Cloudflare アカウント、**アカウント内のアクティブゾーンであるドメイン**、そして
  🚨 **無料プランでも支払い情報の入力**（「Zero Trust Free プランを選んだ場合も
  このステップは必要だが課金はされない」）。partial/CNAME ゾーンは Business プランなので
  現実的にはネームサーバの完全委譲
- **無料枠 50ユーザ**、有料 $7/user/月。51人目から「追加ユーザのログインがブロックされる」。
  **落とし穴: 「既定では非アクティブユーザは自動削除されない」** — 離脱ユーザが黙って席を占める
- **エッジで強制されるので未認証リクエストはオリジンに届かない。
  ただし強制はホスト名スコープでトンネルスコープではない。**
  同じトンネルUUIDを指す別のDNSレコードがあれば、それが未認証の侵入経路になる
- **効く設定2つ:**
  1. **`cloudflared` の `access` オリジンパラメータ**（`required: true`, `teamName`, `audTag`）—
     「オリジンにトラフィックをプロキシする前に Cloudflare Access JWT の検証を `cloudflared` に要求する」。
     **単一設定で最もレバレッジが高い**
  2. **オリジン側での JWT 検証**。`Cf-Access-Jwt-Assertion` **ヘッダ**を検証する
     （`CF_Authorization` クッキーは「渡されることが保証されない」）。`iss`、
     **自分のアプリの AUD タグに対する `aud`**、RS256 を確認。
     **鍵は6週間ごとにローテートし7日間オーバーラップするので、fetch してキャッシュし絶対にハードコードしない。**
     **`aud` の確認が load-bearing** — チーム内の*どのアプリ*の JWT も同じ JWKS で検証が通ってしまう
- **非ブラウザクライアント:** service token（`CF-Access-Client-Id`/`CF-Access-Client-Secret`、
  ポリシーアクション Service Auth）。**既定の寿命は1年、`forever` も許容値**、50トークン/アカウント。
  🚨 **配布するアプリに埋め込んでは絶対にいけない** — ID もMFAもデバイス束縛も無い、
  完全なRCEを与えるベアラ資格情報
- **ブラウザ + service token は Web プラットフォームの制約で不可** —
  `new WebSocket(url, protocols)` にヘッダ機構が無い。ただし通常のIdPログインなら
  `CF_Authorization` クッキーが same-origin の WS ハンドシェイクに自動で乗るので問題にならない
- 🎯 **より良いネイティブ経路: Access 自体が OIDC プロバイダになる。**
  そして **Cloudflare はまさにこの問題のためのドキュメントを出している** —
  [Authenticate coding agents](https://developers.cloudflare.com/cloudflare-one/access-controls/authenticate-agents/):
  401 + `www-authenticate: Bearer` による **RFC 9728** ディスカバリ、
  **動的クライアント登録**、PKCE S256、**localhost:8400 のコールバックリスナ**、
  15分のアクセストークン + リフレッシュ。加えて `cloudflared access login` / `access curl`
- **モバイルに WARP は不要。** 公開ホスト名のセルフホストアプリはクライアントレスで
  ブラウザのIdPリダイレクトで動く。**One-time PIN は外部IdP不要** —
  ただし2026年の変更で「新しい Zero Trust 組織では OTP が自動有効化されなくなった」
- **WebSocket のアイドルタイムアウトは意図的に非公開**（「いずれの方向にも一定時間
  データが流れないと Cloudflare は WebSocket 接続を閉じる」）。
  よく言われる「100秒」は **HTTP 524 のオリジン応答タイムアウトで別機構**。キープアライブが明示的に推奨されている。
  Access のセッション期限が in-flight の WebSocket を殺すかは**未文書**

**判定: 技術的には強いが、独自ゾーン + 支払い情報の必須要件が
「サインアップ不要のOSSツール」の主経路として失格させる。
既にドメインを Cloudflare に置いているユーザ向けの上級オプションとして文書化する。**

## 7. アカウントをどこにも作らずに自宅マシンへ届くか

| | 真にゼロサインアップ? | 落とし穴 |
|---|---|---|
| **LAN / mDNS のみ** | **○** | モバイルのTLS信頼。🚨 **Android Chrome はユーザインストールのCAを任意サイトに対して尊重しない** — モバイル*Web*クライアントにはほぼハードブロッカー。iOS も分かりにくい2段階の信頼フローが必要 |
| CF quick tunnel | **○** | in-flight 200・SSE無し・SLA無し・再起動でURL変更・**Access で保護できない** → 未認証RCEエンドポイント |
| **WebRTC + 公開STUN** | **STUNは○** | **signaling は決して無くせない** — ランデブーを我々が出すか、ユーザが手でSDPを運ぶ。**約10%のネットワークが TURN を必要とし、無料でアカウント不要の TURN は実質存在しない** |
| iroh + n0 relays | **○** | レート制限・SLA無し・「開発とテストのみ推奨」。**ブラウザ/WASM 対応が未確認** |
| 既に持っているVPSに自前リレー | 既に持っている場合のみ | 無ければVPSアカウント+支払い手段 |
| Tailscale 無料枠 | **×** | SSO IdP アカウントが必要。**メールでのサインアップすら不可** |
| **ユーザ自身の無料CFアカウントにリレー** | **×** | **だが: ドメイン不要（`workers.dev`）、かつ Workers Free は Zero Trust Free と違って支払い情報が不要（※要確認）** |

**正直な答え: あるが2通りだけで、両方に実在する落とし穴がある。**
LAN限定は真にアカウントレスだが Android の CA 信頼で詰む。
WebRTC + 公開STUN は*ユーザにとって*アカウントレスだが**我々が signaling を運営する必要があり、
約10%のネットワークが無料フォールバック無しで到達不能。**

🎯 **そして Cloudflare 側に非自明な利点がある: Workers リレー経由にすると LAN の TLS 問題が解決する。**
スマホは有効な公開証明書を持つ Cloudflare のホスト名に `wss://` で話すので、
**secure context（WebCrypto、service worker）が証明書の曲芸ゼロで満たされる。**
これは NAT越えだけでなく **LAN直結に対する本質的な優位**。

## 推奨と D7 への影響

**Tier 2（ユーザ自身の無料 Cloudflare アカウントにワンクリックデプロイ）を推奨する。**

[review-findings.md](review-findings.md) #7 は「D7 のサインアップ不要が、
リモート経路では全部第三者アカウントを要求するので成立していない」という指摘だった。
**Tier 2 はこれを部分的に解く** — アカウントは必要だが**我々のではなくユーザ自身のもの**で、
ドメインも支払い情報も不要、費用ゼロ、そして**我々もCloudflareも信頼経路の外**。
D7 の本来の意図（「どこかのSaaSに登録しないとスマホから見られない、を作らない」）に対して、
「登録するのは*自分の*インフラ」という第3の答えになる。

**ただし正直に書くべきこと: インターネット越しのリモートアクセスについて
「サインアップ不要」は誰にも完全には満たせない。** アカウントレスな経路
（quick tunnel、公開STUN、n0 relays）は全部が明示的に dev/testing でSLA無し。
→ **Tier 0 を本当に優秀なものにして、リモートアクセスを明確にラベル付けされた
アップグレードにする。そしてアカウント無しで製品が壊れて見えないようにする。**

### E2E 設計（交渉不可）

デーモンとスマホが **QRのペアリング秘密から PAKE**（SPAKE2 / OPAQUE）を行い、
その後 **Noise IK** セッションを張る。**リレーは暗号文しか見ない。**
**QRは秘密を直接運ぶ — ペアリングブローカーは作らない。**
両端が DO に*アウトバウンド*で繋ぐ。**DO を作るのはデーモン**で、
`locationHint` は自分のリージョンから決める。

（なお [review-findings.md](review-findings.md) #7 の「QRに鍵材を載せるのは
自分の禁止事項と衝突する」という指摘は、**PAKE にすることで解ける** —
QRが運ぶのは短命なペアリング秘密で、それ自体がベアラトークンとして使えるものではなくなる。）

### Cloudflare に置くもの / 置かないもの

| | |
|---|---|
| **置く** | ドキュメント/Webサイト、オプショナルなリレー Worker + DO |
| **置かない** | バイナリ（GitHub Releases）、更新チェックサービス（静的マニフェスト）、ペアリングブローカー（作らない）、`cloudflared` + Access を主経路にする（独自ゾーン + 支払い情報の要件）、quick tunnel をサポート経路として出荷する |

### 費用

**推奨アーキテクチャでは $0**（ドキュメント無料、バイナリは GitHub、
リレーは各ユーザの無料アカウント）。Tier 3 を50ユーザ分運営するなら
現実的に **$5/月**（アイドル支配で込みの枠内）、
連続ストリーミングが重ければ **〜$29/月**。
費用は duration 駆動なので、**ハイバネーション規律と `setWebSocketAutoResponse` が $5 に保つ鍵。**

### トップ3リスク

1. **ToS §2.2.1(j) の「VPNまたはその他類似のプロキシサービス」。**
   第三者向けに中央運営する暗号文リレーは議論の余地があり、
   Zero Trust 条項は別途転売を禁じている。
   **緩和: ユーザを自分のアカウント（Tier 2）に寄せ、Tier 3 は小さく保ち、
   トンネリングサービスではなく自社製品のトランスポートとして位置づける。**
   **このリスクは Tier 3 が作り、Tier 2 が消す — Tier 2 を推奨する主な理由。**
2. **「サインアップ不要」はインターネット越しのリモートアクセスについて、誰にとっても完全には満たせない。**
   緩和: Tier 0 を本当に優秀にし、アカウント無しで製品が壊れて見えないようにする
3. **リレーの脆弱性と RCE のブラスト半径。**
   Worker のデプロイが**全アクティブセッションを切断**し、DO の配置は作成時固定
   （誤ピンで恒久的に +250ms）、DO は接続中に evict されうる、
   無料プランは「いかなる損害についても責任を負わない」。
   そして RCE 経路上のリレーのバグは致命的。
   **緩和: 再接続+リジュームをプロトコルプリミティブにする。
   リレーは鍵も平文も持たない愚かな信頼されないパイプとして扱う。
   トランスポートとは独立にデーモン側で認可する。
   長寿命ベアラ秘密ではなくセッション毎の capability トークンにする。**
