# 非機能要件（応答時間）の線

**線を勘で引かずに測ってから引く。** 実測して、支配要因を特定して、
それを固定するテストを置く、という順序で決めた。

---

## 実測（2026-08-03、Windows 11 / Node 24 / git 2.48）

`/api/v0/state` の応答時間。12回ずつ。

| | worktree | 衝突ペア | git 起動 | fresh 収集 | キャッシュ経由 |
|---|---|---|---|---|---|
| このリポジトリ | 3 | 0 | 14 | 中央 195ms / p95 204ms | 中央 1ms |
| フィクスチャ | 7 | 4 | 27 | 中央 256ms / p95 268ms | 中央 1ms |

**支配要因はプロセス起動。** ただし「1回 5〜7ms」は**並行実行した場合の実効値**で、
単発のレイテンシではない。別レビュアが直列/並行を分けて実測した:

| | 12ペアの merge-tree | 1ペアあたり |
|---|---|---|
| 直列 | 329ms / 323ms | 27ms |
| 並行 | 65ms / 70ms | 5.4〜5.8ms |

**単発の git 起動は約 27ms、`Promise.all` で並行にして実効 5〜6ms。**
この区別が無いと「並行実行」が効果5倍の主要な対策であることが読めず、
将来誰かが直列化したときに「1回5〜7ms のはずなのに遅い」と混乱する。
payload は 13〜16KB で、転送も JSON 化も無視できる。

## コストの式

```
git 起動回数 = 5（定数）
             + 3 × worktree 本数（**bare / prunable を除く**。status / rev-list / diff）
             + 衝突予測の候補ペア数（merge-tree。上限 12）
             + 1（merge driver の列挙。候補ペアが1組以上あるときだけ）
```

別レビュアが 16 worktree / 12ペアのフィクスチャで検証し、**式と実測が完全一致**した
（`5 + 3×16 + 12 = 65` / 実測 `gitSpawns=65`、1 spawn あたり 5.70ms、
応答は中央 370ms / p95 390ms）。

`stats.gitSpawns` / `stats.conflictPairs` として payload で観測できる。

外挿すると、**worktree 10本・衝突ペア 12組で 47 spawn ≒ 330ms**。

## 引いた線

**「一定のユーザーが使いやすいライン」を次のように定義した:**

| | 目標 | 根拠 |
|---|---|---|
| 想定する規模 | **worktree 10本まで** | 並行して走らせるエージェントの現実的な上限。それ以上は1画面で見ても判断できない |
| fresh 収集 | **p95 < 1000ms** | 外挿で 330ms なので余裕がある。1秒を超えると「押して待つ」感覚になる |
| キャッシュ経由 | **< 50ms** | 15秒ポーリングと複数タブがここを通る |
| 初回表示 | **< 1500ms** | 収集 + 描画。差分は遅延読み込みなので収集がほぼ全部 |
| 端末への追記 | **12,000行で合計 < 12s / 最長ブロック < 400ms** | エージェントの出力は長い。**固まっている間は停止ボタンも自動更新も効かない**ので、合計より最長ブロックが効く |

### ⚠️ この文書はサーバ側しか測っていなかった

上の表の最後の行は後から足した。それまでこの文書は**収集だけ**を測っており、
クライアント側の描画は「速い」とコメントに書いてあるだけだった。
その結果、**出力1件ごとに `scrollHeight` を読んで強制同期レイアウトを起こし、
総文字数に対して二次**になっていた BLOCKING が**どのテストにも掛からなかった**
（実測 12,000行で 53.8秒 / 単一ブロック 28.9秒）。

→ `v0/render-check.mjs` が**実ブラウザ・実時間**で同じ経路（`makeTermWriter`）を叩く。
  現状の実測は **12,000行 = 1216ms / 最長ブロック 42ms / 残った要素 4000**。
  `--virtual-time-budget` では測れない（仮想時間はタイマーを早送りするので
  `performance.now()` の差が作業時間を反映しない）。
  この検査自身が落ちることは `mutate.mjs` の `render-*` 4件で確かめてある。


### ⚠️ もう1つの軸: 分岐した差分の大きさ

「共通ツリーの大きさ」に対しては上の主張どおり緩やか（別レビュアの実測）:

| 共通ファイル数 | merge-tree 1回 | 12ペア並行 |
|---|---|---|
| 3 | 29ms | 73ms |
| 1000 | 31ms | 76ms |
| 20000 | 50ms | 121ms |
| 50000 | 80ms | 179ms |

しかし**両側が 4000 ファイルを触って全部衝突する**ケースは **1ペア 1086ms**（180倍）。
12ペアなら p95 < 1000ms を単独で超える。エージェントが大規模リファクタをする
前提のツールなので、この軸は無視できない。
→ `mergePreview` に 2MB の `maxBytes` を入れ、超えたら `clean: null`（不明）で返す。
  「分からない」を「衝突しない」と偽らないことを優先した。

**この線を守る仕組みは、増やさないことそのもの:**

- **ループの中で git 呼び出しを足さない**（`CLAUDE.md` の規則）。
  ref 解決は `refMap()` の表引き、`$GIT_DIR` は `worktreeGitDirs()` の表引き
- **衝突予測は全ペア（N²）を走らせない。** ファイルが重なるペアだけ、上限 12、並行実行
- **順序提案は追加の git 呼び出し 0。** 既に計算した衝突ペアだけを使う純ロジック
- **TTL キャッシュ + in-flight 合流**で、同時に来た要求は1回の収集に合流する

## テストで固定していること

**壁時計の assert は CI のノイズで揺れる**ので2段構えにした。
厳しい壁時計は flaky になり、緩い壁時計だけでは3倍の劣化を見逃すため。

| 段 | テスト | 何を守るか |
|---|---|---|
| 精度 | `stats.gitSpawns <= 本数×4 + 6 + ペア数` | ループの中で git を増やす回帰を**決定的に**捕まえる |
| 桁 | 収集の中央値 < 2000ms | 桁違いの劣化（同期の直列化、N² 化）を捕まえる |
| 桁 | キャッシュ経由 < 100ms | TTL キャッシュが壊れて毎回収集する回帰を捕まえる |

天井（2000ms / 100ms）は**性能目標ではない**。CI が遅いことを見込んだ
「明らかにおかしい」の線で、目標は上の表の方。

## 線を超えたら何をするか

外挿の範囲では余裕があるが、超えた場合の手はこの順で考える:

1. **`worktreeStatus` を1回にまとめる。** 今は worktree ごとに `git status` を叩いている。
   `--porcelain=v2` を worktree 別に走らせる必要があるので、まとめるには
   ファイル監視で dirty 判定をキャッシュする方向になる（複雑さが増える）
2. **衝突予測を遅延させる。** 初回表示には含めず、パネルを開いたときに計算する
3. **グラフの `--max-count` を下げる。** 今は 300。表示は仮想スクロールにする

**1 を先にやらない。** ファイル監視は複雑さと引き換えなので、
実測で線を超えてから入れる（今は超えていない）。
