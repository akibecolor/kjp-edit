# 認証をいつ入れるか（順序の分析）

**問い:** 今のまま進めて、認証は後から入れられるか。最終的にはリモートから編集したい。

**答え: 大半は後で入れられる。ただし2つだけ「後回しにできないもの」がある。**
retrofit が高いのは認証そのものではなく、**経路の形**。

---

## 後回しにできないもの

### 1. Host ヘッダの検証 → **入れた**（2026-08-02）

**理由: `127.0.0.1` へのバインドと CORS では DNS rebinding を防げない。**

攻撃者のページが自分のドメインの DNS を `127.0.0.1` に貼り替えると、
そのページの**オリジン自体が `127.0.0.1` になる**ので、ブラウザは同一オリジンとして扱う。
CORS ヘッダを返していないことは無意味になる。読み取りだけでも成立する攻撃で、
**ユーザがそのサイトを閲覧しただけでリポジトリの差分が読まれる。**

止められるのは Host ヘッダの検証だけ（ブラウザは元のホスト名を Host に送る）。
攻撃者は自分の持たないホスト名を Host に入れさせられないので、
`--allow-host` によるオプトインでも rebinding は防げたまま。

これは認証と独立で、認証を入れるかどうかに関係なく必要。だから先に入れた。
`v0/smoke.test.mjs` の 🔒 付きテストで固定している。

### 2. 変更・実行する経路を1箇所に絞る → **入れた**（2026-08-02）

**理由: 認証の retrofit コストは経路の数に比例する。**

読み取り専用の今は、経路が増えても危険は増えない（Host 検証は入口で一括判定している）。
だが `POST /checkout` `POST /exec` のような**副作用のある経路を散らしてから**
認証を入れると、全経路を1つずつ監査することになる。1つ忘れると穴が残る。

**規則: 副作用のある経路は必ず1つの関門関数を通す。**
認証を足すときはその関門1箇所を直せば済む。

`v0/server.mjs` の `gateMutation()` がそれ。最初の書き込み操作（checkout）と
同じコミットで作った。要求するのは4つ:

| | 何を防ぐか |
|---|---|
| `--allow-write` | 既定では経路そのものが 403。うっかり有効な状態で起動しない |
| `POST` のみ | リンク・画像・prefetch で副作用が起きない |
| `Sec-Fetch-Site: same-origin` | ブラウザからの他サイト起点 |
| `X-Kjp-Token` | **CSRF 対策の本体。** カスタムヘッダなので cross-origin では preflight が必須になり、CORS を返していないので失敗する。フォーム POST は preflight されないので、これが無いと素通りする |

トークンは起動ごとにランダム（`--token` / `--token-file` で固定も可）。

🚨 **鍵は2種類あり、露出面が違う**（8回目のレビューで分けた）。
以前ここには「標準出力には出さない」「UI は `/api/v0/session` から受け取る」と
書いてあったが、**どちらも実装と逆だった**（案内の URL を stdout に出しており、
UI は `?token=` から受け取る。`/api/v0/session` は「既に生の鍵を提示した要求」に
しか返さない）。実装に合わせて書き直す:

| | 何を通すか | どこに残るか |
|---|---|---|
| 読み取り用の派生秘密（`cookieSecret()`。生の鍵の sha256 由来） | 読み取りだけ | **案内の URL に載せる**ので、アドレスバー・入力履歴・ブックマーク・中継のログに残る。だから読み取りしか通さない |
| 生の鍵（`--token`） | 書き込み・実行・鍵の払い出し | **URL には載せない。** stdout に出し、画面の「鍵を貼る」で sessionStorage に入れる（ポートを含むオリジン単位。タブを閉じれば消える） |

🚨 **読み取りの中にも「生の鍵でしか出さない」ものが1つある: `/api/v0/state` の
`execSessions`。** 一覧には argv（打ったコマンド行そのもの）が入るので、
Cookie / 読み取り用の鍵だけの相手には返さない（Cookie はポートで分離されない）。
⚠️ **落としたら必ず `execSessionsHidden: true` を返す。** UI はこれを見て
「一覧は出せません」と描く。返さないと「1本も走っていない」と**区別できない**ので、
走っているセッションと再接続口が黙って消える（8回目のレビューの SERIOUS。
`--allow-host` のトンネル = 一番使う経路でだけ機能が無い状態になっていた）。
UI 側は `load()` が生の鍵を持っていればヘッダで送る（持っていなければ告知に落ちる）。

⚠️ **stdout には出す。** ローカルの端末に出す前提なので、
**そのログをファイルに落とす運用をしないこと**（`serve.mjs` の出力を
リダイレクトして共有ディスクに置くと、そこが鍵の置き場所になる）。

⚠️ ページは `?token=` を sessionStorage に移して `history.replaceState` で
URL から消すが、**消えるのはカレントの履歴エントリだけ**。
入力履歴・ブックマーク・中継のアクセスログからは消えない。
だから URL に載せる値は読み取り専用にしてある。

| | なぜ後でよいか |

## リモートから「編集」したい場合の順序

読み取りだけなら今のままトンネルで足りる。**編集（書き込み）と実行は別**。

1. **関門を作る**（副作用のある経路はここを必ず通す）
2. **ケイパビリティを既定オフにする。**
   `--allow-write` / `--allow-exec` を明示しない限り経路自体が存在しない
3. **トークン。** 起動時にランダム生成して表示し、
   副作用のある経路だけ必須にする。読み取りは今のまま（Host 検証で足りる）
4. **CSRF 対策。** 副作用のある経路は
   - `Sec-Fetch-Site: same-origin` を必須にする
   - カスタムヘッダを必須にして preflight を強制する
     （フォーム POST は preflight されないので、これが無いと素通りする）
5. **トンネル側で認証。** `tailscale serve`（Tailnet 内）か
   Cloudflare Access。**quick tunnel は使わない**（`docs/hosting.md` §2）

### 実行（exec）— 実装済み（2026-08-02）

**PTY は使っていない。** Node 標準に PTY は無く、`node-pty` は依存を増やす。
そして **Claude Code は `claude -p "..."` で非対話実行できる**ので、
エージェントを遠隔から動かすのに PTY は要らない。
PTY が必要なのは対話 TUI をそのまま覗きたい場合だけなので、その判断は後回しにできる。

`POST /api/v0/exec` は `gateExec()` を通る。`gateMutation()` の4条件に加えて:

| | |
|---|---|
| `--allow-exec` | 書き込みとは**別の** capability。checkout を許すことと任意コマンドを許すことは危険度が桁違い |
| **`--token`（24文字以上）か `--token-file` を明示** | 自動生成を許さない。再起動で変わるトークンでは遠隔運用できず、結果として「楽な場所に置く」方向へ流れる。明示を要求すれば有効化が必ず意識的な操作になり、うっかり起動も防げる |

🚨 **この門は一度成立していなかった**（6回目のレビュー、2026-08-05）。
長さの検査が `if (opts.requireAuth && !opts.token) opts.token = randomBytes(32)` の**後**に
あったので、`--allow-host` は requireAuth を自動でオンにする → **トンネルに出す構成でだけ
門が消えていた**（実測: 43文字の自動生成トークンで `POST /api/v0/exec` が 200）。
見るのは長さではなく **`--token` / `--token-file` で明示したか**（`tokenExplicit`）＋長さの下限。
**門はフォールバックや自動生成より前に置く。順序そのものを変異で測る**
（`exec-token-gate-order`）。
| 既知の worktree のみ | 任意ディレクトリで実行させない |
| `shell: false` + argv 配列 | 引用の崩れと二重解釈を避ける |
| 監査ログ | `<GIT_DIR>/kjp-exec-audit.jsonl` に start / exit を追記 |
| 上限時間 / 同時実行数 | 既定 600 秒（`serve.mjs --timeout <秒>` で延ばせる）/ 8 本 |

⚠️ **「切断で子を殺す」は #17 でやめた。** ここにその行が「テストで固定」と
書いたまま残っていた（既に無い守りを設計文書が保証していた）。
代わりの制約は `v0/execsession.mjs` の1箇所に集めてある:

| | |
|---|---|
| 同時セッション | 8 |
| 絶対上限 | `--exec-timeout`（既定 600 秒）。**keepAlive でも効く** |
| 切断後の猶予 | 既定 300 秒。再購読で延びる。`keepAlive: true` で無効化 |
| 終了後の保持 | 既定 600 秒（出力を読みに戻れる） |
| 終了時の後始末 | 走っているものは木ごと殺す（⚠️ Windows の SIGTERM は既知の限界） |

**allowlist は採らなかった。** `git` を許すだけで
`git -c alias.x='!sh -c ...' x` から任意コードが動くので、ゆるい allowlist は
気休めにしかならない。**扉を守る方に賭ける**方が正直。

### ⚠️ 残っているリスク（実装では消せない）

**`--allow-exec` を有効にした状態で公開トンネルを開けたら終わり。**
`tailscale funnel` / `trycloudflare.com` / 広い `--allow-host` のどれか1つで、
「トンネルに届く相手 = このマシンでコードを実行できる相手」になる。
デーモン側からトンネルの構成は検出できないので、ここは運用で守るしかない。

- トンネルは**必ずループバックで終端**し、**トンネル側で認証**する
  （`tailscale serve` = デバイス ID による認証。Tailnet 内のみ）
- `--allow-host` は必要なホスト名だけ
- 使わないときは `--allow-exec` を外す（起動時に 🚨 を出している）

### ⚠️ PTY を入れるときの注意

**無認証のループバックに PTY を載せると、トンネル設定を1つ間違えた時点で遠隔コード実行になる。**
`0.0.0.0` バインドや `--allow-host` の広い指定や `tailscale funnel` が1つあれば終わる。
だから PTY は 1〜5 が揃うまで入れない。

**代替案（今のスコープと整合する）:**
エージェントを起動するのは既存の端末に任せ、この画面は**出力の観測だけ**を担う。
追記されるログファイルを読むなら書き込み能力はゼロのままで、
「N 個のエージェントを1画面で見る」は成立する。
`v0/layout-prototype.html` のコンソールがモックのままなのはこの判断の反映。

### 総当たりに対する守り（8回目のレビューで作り直した）

7回目に入れたのは「401 を記録する + 連続失敗に指数遅延」だけで、
**遅延は1本ずつを遅くするだけで同時本数を縛らない。**
実測（`--require-auth --token <40字>`、同一 peer から node:http で）:

| | 経過 | 401 | 比較の速さ | 監査ログの増分 |
|---|---|---|---|---|
| 直列 8 本（7回目のテストが見ていた形） | 1,556 ms | 8 | 5 回/秒 | +1.2 KB |
| 並列 300 本 | 2,142 ms | 300 | **140 回/秒** | **+46,092 B** |
| 並列 1200 本 | 2,474 ms | 1200 | **485 回/秒** | **+184,893 B** |

つまり「痕跡ゼロの総当たりを塞いだ」という主張は、**測っていない軸で崩れていた。**
しかも 401 を1本1行で追記していたので、**認証前の要求で `.git` の中のファイルを
外から無制限に伸ばせた**（既定の置き場所は `<GIT_DIR>/kjp-exec-audit.jsonl` =
実行の監査記録と同じファイル）。

今の形:

1. **比較の手前に「認証前の同時本数」の門を置く**（peer ごと 2 本）。
   超えたら**トークンを比較せずに** 429（`Retry-After: 1`）で切る。
   ⚠️ 順序が守りの本体。比較の後ろに置くと 429 が「その値は違った」の同義語になり、
   当てる速さは並列度で決まったままになる
2. 失敗は指数遅延の間**枠を握る**。だから当てる速さの上限は
   `2 本 / 最大遅延 2,000 ms ≒ 1 回/秒`
3. **一度通った資格情報（の SHA-256）は門の外に置く。** 門だけを入れたときは
   持続攻撃（並列50を6秒）の間、**正規のトークンが 15 本中 0 本しか通らなかった**
   — トンネル越しでは peer が全部 `127.0.0.1` なので、peer では攻撃と利用者を
   区別できない。区別できるのは「値を知っているか」だけ。
   素通りするのは**混雑の門だけ**で、`authed()` は必ず通る
4. 401 の記録は窓の先頭 3 本だけ個別に残し、**残りは件数の集約行**にする
   （`event: "auth-failed-summary"`。`suppressed` と `shed` を持つ）。
   追記の本数は要求数ではなく**時間**で縛る（1 peer あたり 10 秒に1行）
5. 監査ログ自体に上限（既定 4 MB / `--audit-max-bytes`）と回転（`.1` に1世代）。
   回転は記録を捨てる操作なので、新しいファイルの先頭に
   `event: "audit-rotated"`（`discardedPrevious` 付き）を書く

修正後の実測: 並列 300 本 → 401 は **5 本** / 429 が 295 本 / 監査 +1,599 B、
持続攻撃（並列12を2.5秒。要求 3 万本超）→ **1.8 回/秒** / 監査 +645 B /
**正規のトークンは全部 200**。

⚠️ **残っている穴を隠さない。** 攻撃が始まった**後**に初めて認証する端末
（まだ1度も通っていない値）は 429 になりうる。再試行が要る。
「唯一の壁がトークン」である以上、当てる速さを縛る方を優先している。

### 同じ守りを実行・書き込みの壁にも掛けた（9回目のレビュー / #48）

**上の3点セットは「読み取りの壁」（`authed()` = 401）にしか無かった。**
実行・書き込みの壁（`gateMutation()` = 403）には遅延も記録も並列の門も無く、
**痕跡ゼロで総当たり**できた。

🚨 **効く相手が「読み取りの鍵を持っている人」であることが重要。**
入口の `authed()` は**案内 URL に載る読み取り専用の派生秘密**でも通る。
その値はアドレスバー・履歴・ブックマーク（クラウド同期）に残るので広く出回る。
つまり **read → exec の昇格路**が開いていた（capability の分界そのものが壊れる）。
「唯一の壁になるものには下限・記録・遅延を必ず付ける」を読み取り側で学びながら、
**危険度が1桁上の実行側に適用し忘れていた**（「規則を書いた場所から遠いコードには
適用し忘れる」型。今回で3件目）。

実測（同じ機械・同じ手順。読み取り鍵の Cookie を持った相手として
`POST /api/v0/exec` に並列 1200 本）:

| | 経過 | 比較された（403） | 切った（429） | 監査ログの増分 |
|---|---|---|---|---|
| 修正前 | 479 ms | **1200 本**（= 2,505 回/秒） | 0 | **0 B（痕跡ゼロ）** |
| 修正後 | 869 ms | **6 本** | 1194 | 682 B |

実装は `v0/failtracker.mjs` に1つだけ置き、**壁ごとに1つ作る**
（`makeFailTracker` / `makeInflightGate` / `makeGoodSet`）。

🚨 **数と遅延を壁の間で共有してはいけない。** 別の capability の壁なので、
混ぜると「読み取りの失敗で実行が絞られる」「その逆」が起きる。
控え（一度通った値）も**別**にする — 読み取り側の控えは読み取り鍵でも真になるので、
使い回すと読み取り鍵を持つ相手が混雑の門を素通りして総当たりを続けられる
（変異 `mutation-reuses-read-goodset` がこれを測る）。

⚠️ 関門の名前を `requireMutation` → **`gateMutation`** に変えた（`requireExec` →
`gateExec`）。async にしたので、**`await` を付け忘れた呼び出しが残ると
Promise が truthy になって門が黙って素通りする。** 名前を変えれば
付け忘れは `ReferenceError` で必ず落ちる（意志ではなく仕組みで防ぐ）。

⚠️ 残る穴は読み取り側と同じ: 攻撃が始まった後の**初回**の実行は 429 になりうる
（まだ「通った値」として覚えられていない）。再試行で通る。

### 最小エディタ（2026-08-06）— 門の順序をどう決めたか

`v0` で**初めて「作業ツリーにファイルの中身を書く」経路**。
読む側（`/api/v0/file`）も**同じ capability の中**に置いた
（`fs` で作業ツリーを読む唯一の経路なので、読み取り専用のデーモンには存在させない）。

両方が `gateMutation()` → `requireEditTarget()` を必ず通る。順序と理由:

| 門 | なぜその位置か |
|---|---|
| 1. `gateMutation()`（認可） | **本文を読む前**。後ろに置くと (a) 未認可の相手がエラーの違いから「そのパスが追跡されているか」を引き出せる（存在の走査）(b) 未認可の相手に 4MB の本文を送らせる。`--allow-exec` の門が自動生成より後ろにあって消えていたのと同じ型なので、**順序そのものを変異で測る**（`write-gate-order`） |
| 2. `isSafeRepoPath()` | 後段（git と fs）が全部この値を使うので、通っていない値を一切渡さない |
| 3. 既知の worktree | 知らないディレクトリを基準にパスを解決しない |
| 4. **git の追跡下**（`ls-files --error-unmatch`） | `fs` で**開く前**。これが「未追跡の `.env` に触れる経路を作らない」という不変条件の本体。ディレクトリを渡すと下のファイルが並んで exit 0 になるので、**出力に「まさにそのパス」があることまで**見る |
| 5. 実体（realpath 包含 / lstat / `O_NOFOLLOW`） | 追跡下でも**中身が symlink なら実体はリポジトリ外にありうる**（`git update-index --cacheinfo 120000` でコミットできる）。3段あるので変異は束ねて外す |
| 6. 中身（512KB / バイナリ / 改行混在） | 混在は「どちらに寄せても触っていない行が変わる」ので直さず 409 |
| 7. 楽観ロック（`baseOid`） | 書く直前。**形（40桁 hex）を先に見てから**比較する |

🚨 **楽観ロックはこの経路の存在理由。** N 本の worktree で N 個のエージェントが
動く前提なので、開いてから保存するまでの間に**そのエージェント自身が書き換えているのが
普通の状態**。黙って上書きするのは「止めたつもりで走り続けている」と同じクラスの誤り。

⚠️ **残っているリスク（実装では消せない）**: 検査と `open` の間にディレクトリを
差し替える競争は塞げていない（`O_NOFOLLOW` は最終要素にしか効かず、Windows には無い）。
同じマシンで動く別プロセスが敵なら防げない — この経路は
「同じマシンの自分のエージェント群」を前提にしている。

checkout は既知の worktree のパスしか受け付けない（任意のディレクトリで git を走らせない）。
拒否する条件は、rebase / マージ未コミット / cherry-pick / revert / bisect の進行中。
**git はこれを exit 0 で通すが、続きの `rebase --continue` は別ブランチにリプレイし、
`MERGE_HEAD` は無警告で消える。** v0 がそれを警告として検出しているのに
自分の checkout で起こしたら本末転倒なので、ここで止める。

### 残っている運用上の判断（利用者が決める）

- **`--allow-write` をトンネル越しに有効にするか。**
  有効にすると、そのトンネルに届く相手はブランチを切り替えられる。
  読むだけなら付けない。起動時に警告を出している
- **トークンをどう持ち回すか。** UI は自動で取るので操作は不要。
  `curl` で叩くなら `--token` で固定する方が扱いやすい
- **PTY（実行）はまだ入れていない。** 1〜4 が揃ったので技術的には次の段だが、
  遠隔コード実行の的になるので、入れる価値があるかを別に判断する。
  「既に走っているエージェントのログを読むだけ」で足りる可能性がある
