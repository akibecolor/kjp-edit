# エージェント活動の観測 — 設計（実装前）

**問い**: 「N 個のエージェントを1画面で見る」のうち、**git の状態は見えているが
エージェントが今何をしているかは見えていない**。これをどう埋めるか。

**結論**: **Claude Code が自分で書いているセッション記録を読む。**
PTY も exec も要らない。ただし**リポジトリ外を読む**ことになるので、
これまで守ってきた不変条件を1つ破る。そこを明示的に設計する。

---

## 何が使えるか（実測、2026-08-03）

```
~/.claude/projects/<slug>/<sessionId>.jsonl
```

- `<slug>` は cwd から作られる（`C:\Users\akico\Documents\kjp-editor`
  → `C--Users-akico-Documents-kjp-editor`）。**大文字小文字は正規化されていない**
  （実際に `C--Users-...` と `c--Users-...` が混在していた）→ 照合は case-insensitive で行う
- **1セッション1ファイル。ライブで追記される**（観測中のファイルが 23MB あった）
- 1行1 JSON。使えるフィールド:

| フィールド | 使い道 |
|---|---|
| `cwd` | **どの worktree の活動か**（これが対応付けの鍵） |
| `timestamp` | 最終活動時刻、待機の判定 |
| `type` | `assistant` / `user`（`user` はツール結果の戻りも含む） |
| `message.content[].type` | `tool_use` / `tool_result` / `text` |
| `message.content[].name` | ツール名（実測: `Bash`, `Edit`, `Write`, `PowerShell`） |
| `sessionId` / `uuid` / `parentUuid` | 同一セッションの追跡 |
| `agentId` / `isSidechain` | **サブエージェントの活動**（親と分けて数えられる） |
| `slug` / `version` / `effort` | 参考情報 |

### ⚠️ `gitBranch` は使わない

実測で **`gitBranch: "HEAD"`** が入っていた（その worktree は `main` に居るのに）。
ブランチ名として信頼できないので、**worktree の対応付けは `cwd` だけで行う。**
`cwd` は `samePath()` で照合する（8.3 短縮名・シンボリックリンク・区切り文字の
差を吸収する既存の関数がそのまま使える）。

---

## 何を画面に出すか / 出さないか

**記録には会話の全文が入っている。** ここを間違えると、トンネル越しに
繋がる相手へ全部を渡すことになる。**「何をしているか」だけを出し、「何を言ったか」は出さない。**

### 出す

| | 例 |
|---|---|
| 最終活動からの経過 | `agent-a: 2分前` |
| 状態 | `実行中` / `待機（12分）` / `記録なし` |
| 直近のツール名 | `Bash`, `Edit`, `Read` |
| 操作対象のパス | `v0/git.mjs`（**リポジトリ相対に丸めたもの**） |
| ツール呼び出しの件数 | 直近5分で 23 回 |
| サブエージェントの本数 | `サブ 2本` |

パスを出す判断: **既にファイラと差分で同じ情報を出している**ので、
新しく漏れる情報ではない。ただし `isSafeRepoPath()` を通り、
かつリポジトリ配下のものだけに限る（リポジトリ外を触っていた場合は
`(リポジトリ外)` と表示してパスは出さない）。

### 出さない（交渉不可）

- **`text` ブロックの本文**（アシスタントの発話、ユーザのプロンプト）
- **`tool_result` の中身**（ファイルの中身、コマンド出力）
- **`thinking`** があれば当然出さない
- ツール入力のうち**パス以外**（`Bash` の command、`Edit` の old/new string、
  `Write` の content）

つまり payload に載せるのは**列挙可能な値と時刻とパスだけ**。
自由文は1文字も通さない。実装では**許可リスト方式**にする
（「これを除く」ではなく「これだけ入れる」。除外方式は新しいフィールドが
増えたときに漏れる）。

---

## 🔒 破る不変条件と、その代わりに置く制約

これまで読み取り側は **`fs` で読まず `git cat-file` 経由**という不変条件で
「リポジトリ外も未追跡の `.env` も読めない」を担保していた
（`docs/review-write-exec.md`）。**これを破る。**

代わりに置く制約:

1. **既定オフ。** `--watch-agents` を付けない限り経路が存在しない
   （`--allow-write` / `--allow-exec` と同じ形）
2. **読む場所を1つに固定。** `~/.claude/projects/` 配下のみ。
   パスは組み立てずに `readdir` で列挙し、`.jsonl` 以外は開かない
3. **末尾だけ読む。** 既定 256KB。全文パースはしない（23MB あった）
4. **許可リストで抽出する。** 上の表以外のフィールドは payload に入れない
5. **書かない。** 読み取りのみ。記録を消したり触ったりしない
6. **`--watch-agents` を有効にすると起動時に警告を出す。**
   「エージェントのセッション記録（会話を含むファイル）を読みます。
   画面に出すのは活動の要約だけですが、読む対象はリポジトリ外です」

⚠️ **これは `--allow-exec` ほどではないが、読み取りの範囲を広げる変更**なので
capability を分ける。`--allow-write` に相乗りさせない。

## 実装の形

### 探索（spawn 0）

```
worktree の path（既に payload にある）
  → slug に変換（`:` と区切りを `-` に）
  → ~/.claude/projects/<slug>/ を readdir（case-insensitive で照合）
  → mtime が最新の *.jsonl を選ぶ
```

⚠️ slug の変換規則は**推測**なので、変換で当てるのではなく
**`projects/` を1回 readdir して、各ディレクトリの中の1行目の `cwd` で対応付ける**
方が確実（規則が変わっても壊れない）。1行目だけなので安い。

### 読み取り（spawn 0、fs のみ）

- 各ファイルの**末尾 256KB** を読む
- 行に分割し、**先頭の不完全な行を捨てる**（末尾から読むので必ず1行目は途中）
- 新しい順に走査し、`tool_use` を見つけたら最新の活動として採る
- 上限件数（例 200 行）で打ち切る

### コスト

**git の起動は 0。** fs の読み取りだけなので `docs/performance.md` の
コスト式（`5 + 3N + P + 1`）は変わらない。
ただし**別の軸が増える**ので測って線を引く:

- worktree N 本 × 256KB の読み取り = N × 256KB
- 10本で 2.5MB。SSD なら数十 ms の想定だが**実測してから線を書く**
- TTL キャッシュ（1.5秒）に乗せる。ポーリングごとに読み直さない

### 失敗の形（全部「黙って消えない」ようにする）

| | 扱い |
|---|---|
| その worktree の記録が無い | `記録なし`（エラーではない。エージェントを走らせていないだけ） |
| `~/.claude` が無い | `--watch-agents` を無効化し `errors` に理由を出す |
| ファイルが巨大 | 末尾だけ読むので影響なし。読めた範囲で判断する |
| 末尾の行が書き込み途中 | JSON パース失敗として捨てる（次のポーリングで読める） |
| 記録が古い（数日前） | `最終活動 3日前` と出す。「今動いている」と誤解させない |
| cwd がどの worktree にも一致しない | 無視（他プロジェクトの記録） |

## テストの計画

**この機能は「出してはいけないものを出さない」ことが本体**なので、
そこを固定するテストを先に書く。

1. **payload に自由文が1文字も入らないこと。** 記録に
   `INJECT-SECRET-12345` を含む `text` と `tool_result` を仕込み、
   payload 全体を JSON 化して**その文字列が含まれないこと**を assert する
   （許可リスト方式が効いているかの検査）
2. `--watch-agents` なしでは経路が存在しない（フィールドが payload に無い）
3. 末尾だけ読むこと（10MB のダミー記録で応答時間が悪化しないこと）
4. 書き込み途中の行（末尾が壊れた JSON）で落ちないこと
5. cwd の照合が `samePath` 経由であること（短縮名・リンクで一致する）
6. 記録が無い worktree が `記録なし` になり、`errors` を汚さないこと
7. **突然変異**: 許可リストを「除外リスト」に変えたら 1 が落ちること

## この設計で答えられること / 答えられないこと

**答えられる**: 「agent-b は 12 分止まっている」「agent-a は今 `v0/git.mjs` を編集している」
「agent-c はサブエージェントを2本走らせている」「agent-d は記録が無い（まだ走らせていない）」

**答えられない**: 「なぜ止まっているのか」（プロンプト待ちなのか、
考えているのか、落ちたのか）。記録から**待機の理由**までは読めない。
理由が要るなら、そこが初めて PTY（または権限プロンプトの検出）の
検討に値する場面になる。

**つまりこの設計は「PTY が本当に必要かを判断するための材料」でもある。**
これを数日使って「止まっている理由が知りたい」と思うなら PTY、
「止まっていることが分かれば端末を見に行けば十分」なら PTY は不要。
